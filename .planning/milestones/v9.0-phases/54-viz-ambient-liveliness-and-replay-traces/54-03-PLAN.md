<objective>
Add an idle-replay scheduler to `src/viz/server.ts` that, during idle gaps, re-emits recent REAL `activation_trace` rows over the existing `/events` SSE tagged `replay: true`. It stays strictly inside the viz server's hard read-only / no-engine / no-LLM / no-fetch boundary by replaying from an in-memory ring buffer populated by the live poll — it opens no new DB handle and never rewinds the forward-only cursor.

Purpose: Give the brain real (but past) activity to echo at idle without crossing the server boundary or fabricating data. The client (Plan 02) renders these `replay:true` rows as a dimmer echo.
Output: a `replayBuffer` ring + an idle-gated replay `setInterval` that broadcasts `{...row, replay:true}` to SSE clients; the live poll populates the buffer and resets the idle timer.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| viz server → DB | Read-only handle only (`new Database(dbPath,{readonly:true})`). Replay must add no second handle and no write path. |
| viz server → engine/LLM/network | Hard no-engine/no-LLM/no-fetch boundary. Replay re-reads in-memory rows only. |
| /events cursor | Forward-only stream cursor; replay is a side-channel and must not rewind it. |

## STRIDE Threat Register

This is the phase's primary threat surface, and per the security brief it is really the boundary-preservation invariant — no high-severity EXTERNAL threats exist (read-only, no untrusted network input, local single viewer). Stated explicitly.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-54-05 | Tampering | /events cursor | mitigate | Replay scheduler reads only `replayBuffer`; source-text guard asserts no `cursor` assignment inside the replay interval. Cursor stays forward-only. |
| T-54-06 | Elevation/Tampering | server read-only boundary | mitigate | Guard asserts exactly one `new Database(` (the readonly handle) and no `fetch(`/`embed(`/`provider` in server.ts. Replay reuses the in-memory ring. |
| T-54-07 | Spoofing | replayed rows | mitigate | replayBuffer is filled ONLY from rows the live poll fetched from the real DB — replay cannot forge arbitrary rows; no user input feeds it. |
| T-54-08 | Denial of Service | SSE backpressure | accept | Single local viewer; replay uses the same `res.write` path as the existing poll. No new exposure (research Open Question 2). |
</threat_model>
