<objective>
Build the decision surface and the poll that feeds it: a batched, structured-fields-only Telegram prompt whose tap targets carry the concrete `from → to` transition, produced by a new poll loop with its own tick and its own in-flight guard.

Purpose: this is where approval fatigue is bounded (APPROVE-03) and where automation bias is defended (APPROVE-01/APPROVE-04). The labeled transition on the button is the safety mechanism — a generic "Approve" becomes a conditioned reflex, a "interviewing → rejected" label forces a micro-read.
Output: v3 callback codec, belief renderer, the bridge pass with entity+day batching, and a default-OFF config gate wired to its own timer.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| recense serve → renderer → Telegram | Email-derived, model-extracted free text is composed into a message a human will act on |
| poll loop → Telegram Bot API | Outbound sends triggered without any human in the loop |
| state/store files → poll loop | On-disk ledger and store drive whether a prompt is suppressed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-68-07 | Tampering | `renderBeliefDecisionMessage` | mitigate | Structure spoofing: a quote carrying newlines plus a forged field line. `asDisplayText` collapses all whitespace and caps length; field order is fixed and the quote is delimited and rendered last within its block. Transport sets no parse_mode, so markup cannot execute — a test asserts `parse_mode` appears nowhere in the new modules |
| T-68-08 | Elevation of Privilege | tap-target design | mitigate | Automation bias is the phase's named risk (Pitfall 7). Buttons carry the transition, one prompt per entity per day, and the existing daily cap applies to belief prompts too. Verified by a test asserting no bare 'Approve' label exists |
| T-68-09 | Spoofing | wire-shape and schema gates | mitigate | A response that is not the frozen v66 contract stops the pass with nothing applied — never coerced, never partially applied (67's D-07 discipline) |
| T-68-10 | Denial of Service | prompt flooding / oversized message | mitigate | Per-entity-per-day ledger, 10-constituent cap per message, 280-char quote cap, existing `tryReserveProposalSlot` daily cap — an inbox burst cannot translate into a burst of interruptions |
| T-68-11 | Tampering | store-first-then-send ordering | mitigate | Rows are written before the send so no button can reference a missing row, and rolled back on send failure so a lost message cannot become a permanently suppressed proposal |
