<objective>
Make a fresh account's backfill batch consolidate oldest-first, so an older message in that batch cannot
apply over newer state.

Purpose: EMAIL-04, second half — the half that actually delivers the success criterion.

**A correction to the research, which the executor must understand before writing any code.**
`.planning/research/PITFALLS.md` Pitfall 5 (line 123) proposes: "during the FIRST backfill for a newly-
onboarded account, sort the fetched message batch by `Date:` header before appending, so within-run
ordering matches chronological order." **That fix does not work in this codebase.** Consolidation order is
not append order. `EpisodicStore.listUnconsolidated` (`src/db/episode-store.ts:124-126`) is
`SELECT * FROM episode WHERE consolidated = 0 ORDER BY hard_keep DESC, salience DESC` — the D-03/D-10
replay-priority order — and `Consolidator.consolidate()` slices that list in index order into prefetch
chunks and processes the per-episode loop strictly in that order (`consolidator.ts:531`, and the
"EPISODE ORDER IS SEMANTICS" comment at :551-558). Salience is uncorrelated with send time, so sorting at
append time would be discarded entirely by the very next `ORDER BY salience DESC`. The fix has to land at
the consolidation seam. Do not implement the append-time sort; it would be dead code that looks like a fix.

Output: a pure, permutation-safe reordering function and its single call site in `consolidate()`, plus the
end-to-end regression test that proves the stale-evidence case is closed.
</objective>

Create `src/consolidation/episode-order.ts` exporting
`orderEpisodesForConsolidation(rows: readonly EpisodeRow[]): EpisodeRow[]`.

Algorithm — slot-preserving chronological reorder:
1. Walk the input once, collecting the indices at which `row.event_ts !== null && row.event_ts !== undefined`.
2. Take the rows at those indices and sort them by `event_ts` ascending, tie-breaking on `id` ascending
   so the result is fully deterministic for equal timestamps (two messages can legitimately share a
   `Date:` value to the second).
3. Copy the input into a new array, then write the sorted rows back into exactly the collected indices,
   in order.
4. Return the new array. Never mutate the input array or any row object.

Why slot-preserving rather than a global chronological sort — this reasoning belongs in the file's doc
block, because the naive alternative looks simpler and is wrong: the positions themselves still express
the D-03/D-10 replay priority (`hard_keep` first, then salience descending). A truncated pass — budget
cap, lock-stale restart, `FIX-STALL-01` chunk boundary — still processes the same PREFIX of the list, so
the same high-priority episodes still get consolidated first and the same count gets done. What changes
is only WHICH email occupies which email-slot, and that is exactly the defect being fixed. A global
chronological sort would instead let a low-salience months-old backlog message displace a high-salience
recent episode out of a truncated pass. Also document the guarantee that non-Gmail episodes, which all
carry `event_ts === null` today, are provably untouched — that is what makes this change safe to apply
unconditionally to every pass rather than gating it behind a "is this a backfill?" heuristic, which
would itself be a source of bugs.

Also document the residual honestly in the same doc block: this orders within ONE pass's unconsolidated
set. Episodes appended in a later pass, or a second account's backfill landing in a different pass, are
not ordered relative to already-consolidated episodes. The routing-side defence for that case is
DRIFT-04 in Phase 65. Name it as a known residual, not as covered.

- Empty array and single-element array are no-ops.
- Permutation property: for a shuffled 50-row mixed fixture, output length equals input length and the
