<objective>
Deterministically strip markup and hidden content from every Gmail body at the ingest boundary, so
text a human cannot see in Gmail is not present in the token stream a future classifier reads.

Purpose: EMAIL-03, and a hard prerequisite for Phase 63 — classification is the first LLM consumer of
this content that an attacker can actually steer. `extractBodyText` (`src/source/gmail-adapter.ts:100`)
recurses for a `text/plain` part and then falls through at :113-116 to `part.body?.data`, which returns
raw HTML whenever the message is HTML-only — the common shape for ATS and recruiting-system mail.
`redactSecrets` is regex-scoped to secrets and blind to markup semantics, so a `display:none` div, a
zero-width-joined payload, or a class-hidden span reaches the model intact today. This is the
EchoLeak-class indirect-injection vector, and email content is untrusted by construction: `origin` is
hard-coded `observed` (D-61), never `asserted_by_user`.

Output: a new pure module `src/source/strip-hidden.ts`, its unconditional application inside
`normalizeGmailMessage`, and a named regression fixture whose hidden instruction must not survive.
Deterministic and LLM-free per CLAUDE.md — ingest is an online path.
</objective>

Create `src/source/strip-hidden.ts` exporting `stripHiddenContent(text: string): string`, structured
as an ordered pipeline of stages. Compile every regex ONCE at module load into named module-level
constants, following `redact.ts`'s compile-once discipline, and reset `lastIndex` before each use of
any global regex for the same reason `redactSecrets` does.

Stage order (the order is load-bearing; document why in the file):

1. **Invisible codepoint removal**, applied unconditionally to all input including plain text.
   Remove: U+200B ZERO WIDTH SPACE, U+200C ZWNJ, U+200D ZWJ, U+2060 WORD JOINER, U+FEFF BOM/ZWNBSP,
   U+00AD SOFT HYPHEN, U+180E MONGOLIAN VOWEL SEPARATOR, U+2061–U+2064 invisible math operators, and
   the entire Unicode Tags block U+E0000–U+E007F. The Tags block is the "hidden Unicode instruction
   injection" carrier named in the 2026 CSA research; it renders as nothing at all and is pure payload.
   This runs FIRST so a payload cannot use zero-width characters to break up a later stage's pattern
   match (for example `dis<ZWSP>play:none` defeating the hidden-style detector).

2. **CSS hiding-selector harvest**, before any `<style>` block is discarded. Scan `<style>` blocks for
   simple rule blocks whose body matches a hiding signature (see stage 5) and whose selector list is
   composed only of bare single class (`.name`) or id (`#name`) selectors — no combinators, no
   pseudo-selectors, no attribute selectors, no media queries. Collect those names into two sets. Bound
   the harvest (cap at 200 selectors) so a pathological stylesheet cannot cause quadratic work. This
   stage exists because the realistic ATS shape hides a span by class, not by inline style, and simply
   deleting the `<style>` block would destroy the evidence that the span is hidden while leaving the
   span's text behind.

3. **Comment removal.** Delete `<!-- ... -->` spans. An unterminated `<!--` deletes to end of string
   (fail-safe: less content).

4. **Non-content element removal, with contents.** Delete `<script>`, `<style>`, `<head>`, `<title>`,
   `<template>`, `<noscript>`, and `<svg>` elements together with everything between open and close
   tag, case-insensitively. An unterminated open tag deletes to end of string.

5. **Hidden element removal, with contents.** For every start tag, treat the element as hidden when its
   start-tag text matches any hiding signature. Signatures, all case-insensitive and whitespace-tolerant
   around `:` and `;`:
     - `display:none`
     - `visibility:hidden` and `visibility:collapse`
     - `opacity:0` where the value is exactly zero (must not match `opacity:0.85`)
     - `font-size:0` where the value is zero with an optional `px`/`pt`/`em`/`rem` unit
     - `height:0`, `max-height:0`, `width:0`, `max-width:0`, same zero-with-optional-unit rule
     - `text-indent:` followed by a negative value
     - `left:` or `top:` followed by a negative value of 3 or more digits (off-canvas positioning)
     - `clip:rect(0` and `clip-path:inset(100%`
     - the bare boolean `hidden` attribute
     - `aria-hidden="true"` (quote style and whitespace tolerant)
     - a `class` attribute containing any name harvested in stage 2, or an `id` attribute equal to a
       harvested id
   On a match: if the tag is self-closing or a void element, delete just the tag; otherwise scan forward
   counting same-name open and close tags to find the matching close tag and delete the whole span. If
   no matching close tag exists, delete to end of string — fail-safe toward less content, never
   passthrough. Bound the forward scan by the remaining string length so malformed nesting terminates.

6. **Remaining tag removal.** Delete every remaining `<...>` sequence. An unterminated trailing `<`
   plus following text deletes to end of string.

7. **Minimal entity decoding.** Decode ONLY `&nbsp;` and `&#160;` to a single space. Every other entity
   is left literal on purpose: decoding `&amp;` or `&lt;` would break idempotence (`&amp;amp;` → `&amp;`
   → `&`, and a decoded `&lt;` would be re-read as a tag on a second pass). Document this tradeoff in
   the file — a stray `&amp;` in prose is cosmetic noise; a non-idempotent boundary function is a
   correctness bug, since `redactSecrets` alongside it is idempotent and callers rely on that property.

8. **Whitespace normalization that preserves paragraph structure.** Collapse runs of spaces and tabs to
   one space, trim each line, collapse 3-or-more consecutive newlines to exactly two, and trim the
   overall result. Do NOT collapse all whitespace to single spaces — plain-text email bodies flow
   through this function unchanged today and their line structure is real signal.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Gmail message content → episode content | THE boundary this plan exists to harden. Email bodies are attacker-controlled: anyone who knows the address can send one. `origin` is hard-coded `observed` (D-61), never `asserted_by_user`, so the engine already treats this content as untrusted — but untrusted content still reaches the model's token stream verbatim today. |

| rendered email (what the human sees) → episode content (what the model sees) | The asymmetry IS the vulnerability. Content invisible in a mail client but present in the DOM is exactly the payload class. |
