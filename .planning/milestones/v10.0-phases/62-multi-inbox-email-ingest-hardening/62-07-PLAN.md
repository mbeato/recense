<objective>
Close the EchoLeak-class bypass in `stripHiddenContent`: an attribute value containing a literal `>` before a
hiding declaration currently truncates the tag match, so `isHiddenStartTag` never sees the
`style="display:none"`, stage 5 records no removal range, and the hidden instruction payload survives verbatim
into the extractor's token stream.

Purpose: closes `62-REVIEW.md` CR-01 (critical). Confirmed still live in shipped source and confirmed
reproducible during planning against the real module:

| input | shipped output | required output |
|---|---|---|
| `<div data-x="a>b" style="display:none">SECRET3</div>Visible.` | `b" style="display:none">SECRET3Visible.` | `Visible.` |
| `<div style="content:'>';display:none">HIDDEN INSTRUCTION PAYLOAD</div>Visible.` | `';display:none">HIDDEN INSTRUCTION PAYLOADVisible.` | `Visible.` |
| `<div data-x='a>b' style='display:none'>SECRET4</div>Visible.` | `b' style='display:none'>SECRET4Visible.` | `Visible.` |

A literal `>` inside a quoted attribute value is legal HTML and common in real mail (`data-*`, `title`, `alt`,
or a CSS string literal like `content:'>'`). Every one of these divs is genuinely `display:none` in a real
renderer, yet the payload text reaches the model today. EMAIL-03 exists to close exactly this vector, and the
95-case suite passes with the bug present.

Output: quote-aware attribute scanning applied consistently to all three tag regexes, regression cases at both
the unit and episode-content level, an explicit no-over-correction lock, and a measured backtracking bound.
</objective>

The three regexes to change, at their current lines in `src/source/strip-hidden.ts`:

- `:100` `const START_TAG_RE = /<([a-zA-Z][a-zA-Z0-9]*)\b([^<>]*)>/g;` — drives `collectRemovalRanges`, which
  feeds `attrs` to stage 4's tag-set predicate and stage 5's `isHiddenStartTag`.
- `:103` `const ANY_TAG_TOKEN_RE = /<(\/?)([a-zA-Z][a-zA-Z0-9]*)\b[^<>]*>/g;` — drives
  `findMatchingCloseEnd`'s nesting scan, which decides where a removed element ENDS.
- `:336` `const ANY_TAG_RE = /<[^>]*>/g;` — stage 6's blanket leftover-tag sweep.

These three must agree on where a tag ends. If only `START_TAG_RE` becomes quote-aware, stage 5 would identify
a hidden element correctly while `findMatchingCloseEnd` mis-locates its close tag, producing a removal range
that is too short or too long — the same class of boundary bug relocated ACROSS stages, which is worse than the
original because it can now also delete visible prose. Consistency across all three is a hard requirement of
this plan, not a nicety.

Note the deliberate asymmetry in the third literal: `START_TAG_RE` and `ANY_TAG_TOKEN_RE` exclude `<` from the
unquoted character class (matching their current `[^<>]`), but `ANY_TAG_RE` must NOT — its current `[^>]*`
permits `<` inside the match, and narrowing that would be an unrelated behavior change. Keep `ANY_TAG_RE`'s
unquoted class as `[^'">]`.
</interfaces>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| untrusted email HTML → `stripHiddenContent` | Email bodies are attacker-controlled by construction (origin hard-coded `observed`, D-61). This function is the sole boundary control between raw sender HTML and the extractor's token stream. |
| `stripHiddenContent` → extractor / future classifier | Anything surviving here becomes model input. A surviving hidden instruction is an EchoLeak-class indirect prompt injection, and Phase 63's classifier will read the same episode content. |
| attacker-controlled input length → ingest CPU | `normalizeGmailMessage` passes the full untruncated body to the stripper; the caller applies no length cap. Input size is chosen by the sender. |
| stage 5 ↔ stage 6 ↔ `findMatchingCloseEnd` | Three regexes independently decide where a tag ends. Disagreement between them is itself an exploitable boundary. |
