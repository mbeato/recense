## Locked decision: extract-and-reuse, not duplicate

`62-VERIFICATION.md` asks the planner to state whether the existing stage-1 implementation can be extracted
without changing `stripHiddenContent`'s own behavior. **It can, and extract-and-reuse is the locked choice.**
Reasons, all checkable rather than asserted:

1. Stage 1 is a single unconditional expression with no branching and no dependence on any other stage's state.
   Moving it into `export function stripInvisibleCodepoints(text: string): string` that returns
   `text.replace(INVISIBLE_CODEPOINTS_RE, '')`, and having stage 1 call it, is a pure inline/outline
   transformation.
2. Sharing the one module-scope `/gu` regex object between two call sites cannot leak `lastIndex` state.
   `String.prototype.replace` with a global regex sets `lastIndex` to 0 before matching and again after
   completion (`RegExp.prototype[@@replace]`), which is the same reasoning `strip-hidden.ts`'s own doc block
   already gives at `:14-17` for its `.replace()`/`.match()`/`.test()` call sites. Task 3 proves this with an
   interleaving test rather than leaving it as an argument.
3. Duplicating the regex would violate the compile-once discipline and create two sources of truth for the
   invisible-codepoint set — a drift hazard on exactly the security control this plan exists to extend.

The alternative — calling the full `stripHiddenContent` on headers — is **rejected**, and the rejection must be
recorded in the corrected comment: headers are not markup, and stages 4-6 would delete a legitimate
`Subject: Re: <urgent> pricing` down to `Re:`, plus stage 8 would collapse whitespace the subject may carry
meaningfully. Stage 1 alone is a pure codepoint delete with no markup semantics and no false-positive risk on a
subject line. Task 1 locks that distinction as a test.
