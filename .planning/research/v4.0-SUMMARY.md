**Researched:** 2026-06-15

---

## Executive Summary

Recense v4.0 turns a validated passive memory engine into one that surfaces and acts — proactively pushing salient/due items to Telegram and, after explicit per-action approval, firing any configured MCP tool. The milestone is achievable with **net-zero new runtime dependencies** (`googleapis`, `@modelcontextprotocol/sdk` client, `zod`, and the raw-fetch Telegram seam are already installed), because the engine surface area is small: two LLM-free serve routes (`GET /v1/surface`, `POST /v1/surface/seen`), a sparse `node_temporal` schema addition, and a `surfaced_event` operational table modeled on the existing `activation_trace` precedent. All agent logic stays in `clients/telegram/` — the engine/client boundary from v3.0 holds without modification.

The core differentiator is **not** the trigger/notify/approve plumbing — Lindy, Khoj, and LangGraph already cover that. The differentiator is the **memory filter**: salience · confidence + PE-novelty + due-proximity deciding *what* to surface. No competitor combines a memory substrate that learned what the user cares about with a HITL gate and any-MCP execution at self-hosted scale. Every design anti-pattern in the research (LLM-in-the-surfacing-path, per-fact user tagging, per-fact LLM scoring) degrades this differentiator by adding cost or noise to a layer the engine already solves better.

The top field risk is **notification fatigue** — the #1 failure mode for every proactive assistant ever shipped. Three-signal gating (salience + PE-novelty + seen-state), a 24-hour re-surface guard, a daily cap of 3 items, and never-empty-digest suppression are load-bearing requirements, not polish. The second risk is **prompt injection** via ingested email content reaching the proposal LLM; injection-hardening delimiters, an approval message derived from the serialized payload, and a per-server allowlist must all be in the first version of the gate — not retrofitted. The **Gmail episodic-variant** prompt change is the only live-DB risk and must stay behind a runtime flag defaulting off, with an offline dry-run A/B comparison before any live write (`gated-live-write-needs-real-offswitch` lesson applies directly here).

## Key Findings

### Recommended Stack

The v4.0 milestone requires **net-zero new runtime dependencies**. `googleapis` + `@modelcontextprotocol/sdk` client + `zod` + the raw-fetch Telegram seam are all already installed.

For v4.0 specifically: the Google Calendar adapter reuses the existing OAuth2 flow from Gmail (Phase 6), adding only a separate `calendar.readonly` scope. The `@modelcontextprotocol/sdk` client is already installed from Phase 11 — the push client instantiates an MCP client handle per configured server. No `npm install` is required before any v4.0 phase begins.

**Core technologies already in place for v4.0:**
- `googleapis` — Google Calendar API v3 adapter (incremental sync, `nextSyncToken` pattern, 410 GONE recovery)
- `@modelcontextprotocol/sdk` (client mode) — MCP tool discovery (`listTools`) + execution on approval
- `zod` — proposal object schema validation (typed args → approval message rendering; prevents LLM free-form re-parse)
- better-sqlite3 (existing) — two new tables: `node_temporal` (sparse temporal metadata on nodes) + `surfaced_event` (operational table, never read by sleep pass)
- existing `brain serve` (Phase 12) — two new routes hang off the existing server; no new HTTP server or framework

### Expected Features

The research cleanly separates commodity plumbing (table stakes every proactive assistant ships) from the memory-filter differentiator (what only recense can do).

**Must have (v4.0 gate — all feature areas required before shipping):**
- Gmail episodic-variant extraction prompt (parallel constant `GMAIL_EPISODIC_EXTRACTION_PROMPT`, feature-flagged `RECENSE_ENABLE_EPISODIC_EMAIL=false`, dry-run validated offline before any live enable)
- Google Calendar `SourceAdapter` (structured, reliable; incremental sync; UTC normalization at ingest boundary; RRULE → pattern-belief not N individual instances; cancellations → tombstone)
- `node_temporal` schema migration: `due_at`/`event_at`, `action_type`/`fact_type` on a sparse extension table; indexed on the temporal column(s)
- `surfaced_event` operational table: surfaced/seen/snooze state — DB-backed, never held in process memory, never read by sleep pass
- `GET /v1/surface` — LLM-free, composite ranking (deadline proximity + salience + PE-novelty), daily cap 3 (P0 bypass for deadline < 24h), exclusion for completed/snoozed
- `POST /v1/surface/seen` — idempotent seen/snooze write-back to `surfaced_event` only (never to `node.s`/`node.c`)
- Proactive Telegram push: P0 immediate, P1 daily digest at configurable hour, never-empty-digest guard, quiet-hours window
- HITL inline keyboard: Approve / Edit / Reject / Snooze with episodic audit trail (`source: 'hitl'`)
- MCP tool discovery + LLM parameterization (one async call, not on a blocking hot path) + execution on approval, per-server allowlist, destructive-tool secondary confirm (typed "YES", not a button)

**Should have (v4.x — needs v4.0 data to validate):**
- PE-novelty as a surfacing signal — needs `last_pe_magnitude` surfaced on nodes; baseline must run first
- Schema-activation surfacing trigger ("I noticed a pattern") — SREL-01/02 machinery ready; needs v4.0 graph data to tune
- HITL feedback → salience adjustment loop — needs approval/reject volume before the loop is trustworthy

**Defer to v5+:**
- MCP Elicitation mid-execution approval (spec draft, limited framework adoption)
- Multiple delivery channels (Slack, email digest)
- Per-schema surfacing frequency learning (requires months of usage data)

**Explicit anti-features (do not build):**
- LLM-in-the-surfacing-path — degrades the differentiator; adds cost on every poll
- Auto-approve after timeout — trust-breaking; the approval gate is not optional friction
- iMessage as ingestion source — structural self-echo loop, rejected in Phase 7
- Per-fact user priority configuration — creates configuration burden; salience + PE signal are the learned priority

### Architecture Approach

The engine/client boundary from v3.0 holds exactly. The engine gains two serve routes and two new tables; all agent logic (polling, push, HITL keyboard, MCP client, proposal generation) lives in `clients/telegram/`. The `surfaced_event` table follows the `activation_trace` operational-table precedent — read by the surfacing route, written by the seen-state route; the sleep pass never touches it; it does not participate in consolidation. This is the load-bearing guard against D-43 self-confirmation.

**Engine-side additions (minimal):**
1. `src/db/schema.ts` — schema migration: `node_temporal` sparse table + `surfaced_event` operational table (+ indexes). (Pin the exact `SCHEMA_VERSION` bump against live code — research saw it at 7→8.)
2. `src/adapter/serve-cli.ts` — `GET /v1/surface` (LLM-free SQL ranking, read-only DB handle) + `POST /v1/surface/seen` (idempotent seen/snooze write-back, write lock)
3. Gmail episodic-variant: second named prompt constant in the D-62 per-source seam, selected by env flag (default off)
4. `src/source/calendar-adapter.ts` — Google Calendar `SourceAdapter`: incremental sync, recurring-event → pattern-belief, cancellations → tombstone, UTC normalization at ingest boundary
5. `src/model/claim-extractor.ts` — extend `ExtractedClaim` with optional `due_at` / `action_type` (backward-compatible)
6. `src/consolidation/consolidator.ts` — upsert `node_temporal` in Phase B when `claim.due_at` is present (synchronous, inside the existing transaction)

**Client-side additions (all in `clients/telegram/`, zero `src/` imports):**
1. Push scheduler: `setInterval` polling `GET /v1/surface`, separate from the `getUpdates` poller (single Telegram consumer per bot → push + pull in one process)
2. Proposal formatter: renders the approval message from serialized `{tool, args}` — not LLM-generated prose
3. HITL inline keyboard handler: validates `chat.id` against the allowlist before processing any callback
4. MCP client: discovers tools via `listTools`, LLM-parameterizes from memory context (`/v1/search`), executes on approval only
5. Audit writer: decisions → episodic log via `POST /v1/add` (`source: 'hitl'`, user-asserted not inferred)

### Critical Pitfalls

1. **Prompt injection / confused deputy** — ingested email with instruction text steers action selection; the approval message describes something different from what executes. Mitigation: delimiter-fenced memory data in the system prompt; approval message rendered from serialized `{tool, args}` (never LLM prose); per-server allowlist. Must be in the first version of the gate.
2. **Approval fatigue → rubber-stamping** — more than ~3 proposals/day trains users to tap Approve without reading; a destructive action slips through. Mitigation: hard daily cap (3/day, P0 bypass), reversible/irreversible label on every proposal, destructive tools require typed "YES" (not a button).
3. **Notification fatigue** — raw salience alone surfaces expired deals and processed receipts. Mitigation: three independent signals must all hold (salience AND PE-novelty AND not-yet-surfaced); schema-saturation cap; past-event guard.
4. **D-43 self-confirmation via surfacing write-back** — reading a belief to surface it must not strengthen `node.s`/`node.c`. Mitigation: `surfaced_event` is the only write target; a D-43 sentinel test (call `/v1/surface` N times, assert `node.s`/`node.c` unchanged) is a required verification criterion before the push client connects.
5. **Gmail episodic-variant regression on live DB** — changing the extraction prompt touches production brain.db with no rollback. Mitigation: `RECENSE_ENABLE_EPISODIC_EMAIL=false` default; offline dry-run on a DB snapshot (~$0.20 at DeepSeek V4-Flash) with explicit pass/fail criteria as a hard prerequisite.
6. **Temporal timezone desync + recurring-event flooding** — bare local-time strings cause wrong-time notifications; RRULE events emitting N beliefs trigger N notifications. Mitigation: ISO 8601 UTC + timezone name at the ingest boundary; Calendar adapter emits a pattern belief for recurring events.

## Implications for Roadmap

Research strongly supports a four-phase sequence ordered cheap-and-safe-first: each phase is independently valuable, near-$0 in new LLM cost, and the live-DB risk is isolated to Phase 1 behind a flag.

### Phase 1: Temporal Ingestion Foundation (~$0)
Zero proactive triggers exist without temporal facts in the graph. Delivers the `node_temporal` schema migration, the Google Calendar `SourceAdapter` (incremental sync, UTC normalization, recurring→pattern, 410 GONE recovery), the `GMAIL_EPISODIC_EXTRACTION_PROMPT` behind `RECENSE_ENABLE_EPISODIC_EMAIL=false`, the `ExtractedClaim.due_at` extension, and a TTL pass marking past events complete. Resolves the live-DB risk early (offline dry-run A/B with pass/fail criteria) while nothing downstream depends on it yet. Avoids Pitfalls 5 and 6.

### Phase 2: Engine Surfacing API (~$0, read-only)
The LLM-free surfacing route is the decision layer everything else polls; it must be verified (D-43 sentinel passing, seen-state DB-backed) before any push client connects. Delivers the `surfaced_event` table, `GET /v1/surface` (composite ranking, daily cap, past-event guard, completed/snoozed exclusion), `POST /v1/surface/seen`, and the **required** D-43 sentinel test. Avoids Pitfalls 6 (self-confirmation), 3 (fatigue), 4 (past-event).

### Phase 3: Notify-Only Proactive Telegram Push (net-zero deps)
Delivery before execution — validate surfacing signal quality and frequency in dogfood before adding the execution surface. Delivers the proactive push loop in `clients/telegram/` (P0 immediate + P1 daily digest, never-empty-digest guard, quiet-hours, seen/snooze buttons → `POST /v1/surface/seen`), launchd `ThrottleInterval` crash-loop guard, and a `RECENSE_PROACTIVE_ENABLED=false` off-switch. Avoids re-notification-after-dismissal and crash-loop pitfalls.

### Phase 4: Approval-Gated Any-MCP Execution
Most complex and highest-risk; builds on Phase 3's validated push flow. Delivers MCP tool discovery (`listTools`, cached per server), LLM parameterization from memory context, the proposal formatter from serialized `{tool, args}`, the Telegram inline keyboard (Approve/Edit/Reject/Snooze), the edit path, destructive-tool secondary confirmation, per-server allowlist, execution-on-approval-only, episodic audit log, proposal expiry, and `chat.id` allowlist validation on every callback. **All security guards ship in the first version.** Avoids Pitfalls 1 and 2.

### Phase Ordering Rationale
- **Dependency chain is strict:** temporal facts → surfacing signal → push delivery → action execution.
- **Cost isolation:** Phases 1–3 are near-$0; Phase 4 introduces one async LLM call per proposal (offline push path).
- **Risk sequencing:** live-DB risk in Phase 1 (behind a flag); D-43 sentinel in Phase 2 (gate for Phase 3); injection security in Phase 4 (gate for first user-visible execution).
- **Architecture preservation:** engine/client boundary holds throughout.

### Research Flags
- **Phase 1:** Google Calendar incremental sync edge cases — `nextSyncToken` vs `nextPageToken`, 410 GONE full-resync handler. Track as verification criteria.
- **Phase 4:** MCP tool security (adversarial tool description / prompt injection via metadata, arxiv 2508.12538) — targeted read before writing the Phase 4 plan to confirm per-server allowlist coverage.
- **Standard patterns (skip research-phase):** Phase 2 (LLM-free SQL ranking fully specified), Phase 3 (standard Telegram push + inline buttons; existing seam handles it).
