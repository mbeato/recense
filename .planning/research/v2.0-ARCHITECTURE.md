## Existing Architecture (read from source)

Before describing what changes, here is what the code actually does — the invariants that the new features must respect.

### System Overview

```
┌─────────────────────────────────────────────────────────────────────┐
│  Online paths (LLM-free, blocks user — latency is felt)             │
│                                                                      │
│  SessionStart     UserPromptSubmit        Stop                       │
│  session-start-cli  turn-capture-cli    stop-cli                     │
│        │                  │                 │                        │
│        ▼                  ▼                 ▼                        │
│  RetrievalEngine   EpisodicStore.append  → spawns sleep-pass-cli    │
│  retrieveCueless()  (sync write)           (detached child)         │
│  (cue-less rank + 1-hop spread — no LLM)                           │
├─────────────────────────────────────────────────────────────────────┤
│  On-demand latency-tolerant recall (one embed + one LLM call)       │
│                                                                      │
│  recall-cli ──► RecallEngine.recall()                               │
│                  embed online (D-41) → topk → schema resolve        │
│                  → 1-hop neighborhood → LLM compose → inferred ep   │
│                  NEVER writes graph facts (ephemeral-as-fact)       │
├─────────────────────────────────────────────────────────────────────┤
│  Offline sleep pass (all LLM/embed cost lives here)                 │
│                                                                      │
│  launchd plist → sleep-pass-launchd.sh → sleep-pass-cli            │
│                   sources env file         acquireLock()            │
│                   (secret-free wrapper)    runConsolidation()       │
│                                            releaseLock()            │
├─────────────────────────────────────────────────────────────────────┤
│  Always-on watcher (long-running, launchd KeepAlive)                │
│                                                                      │
│  watcher-cli ──► Telegram (primary) or iMessage (Mac-only)          │
│                  per-tick lock → receive → HybridResponder → send   │
├─────────────────────────────────────────────────────────────────────┤
│  Storage layer (source of truth)                                    │
│                                                                      │
│  SemanticStore (graph: node + edge)     — sync, prepared stmts      │
│  EpisodicStore (episodes)               — sync, prepared stmts      │
│  CandidateRetriever (brute-force cosine)— sync, read-only           │
│  EventStore (consolidation_event)       — sync, append-only         │
│                                                                      │
│  All writes: single-writer (acquireLock/releaseLock O_EXCL guard)  │
│  DB: WAL mode — concurrent reads during offline write pass OK       │
└─────────────────────────────────────────────────────────────────────┘
```

### Load-bearing invariants (must not break)

| Invariant | Where enforced | Why |
|-----------|---------------|-----|
| Online paths are LLM-free | `RetrievalEngine` — no provider call | SessionStart blocks user; latency is felt |
| Single writer | `acquireLock()`/`releaseLock()` in every CLI | Prevents graph corruption |
| Graph is source of truth | Vector is derived; UI must never write | Consistency across reconsolidation |
| Inferred output never written back | RecallEngine ONLY writes `origin:'inferred'` episode | Self-confirmation loop prevention |
| WAL mode concurrent reads | `db.pragma('journal_mode = WAL')` in initSchema | Sleep pass can write while UI reads |

## New Feature Integration Points

### 1. Scheduler Seam

**What the code actually shows:** The scheduler is entirely external to TypeScript today. `sleep-pass-cli.ts` is a dumb "run once" CLI — it has no awareness of how it was invoked (launchd, cron, or manual). The scheduler contract lives in three shell artifacts:

- `scripts/sleep-pass-launchd.sh` — sources the gitignored env file, then `exec $NODE $SLEEP_PASS_JS`
- `scripts/setup-dogfood.sh` — renders a plist template, calls `launchctl bootstrap`
- `~/.config/brain-memory/sleep.env` — holds `BRAIN_MEMORY_NODE_BIN`, `BRAIN_MEMORY_SLEEP_JS`, `BRAIN_MEMORY_DB`, keys

The slot for the scheduler seam is **entirely in the setup/registration layer**, not in the CLI runner. `sleep-pass-cli.ts` stays unchanged.

**Where it slots in:**

```
Before (macOS only):
  setup-dogfood.sh
    → renders plist template
    → launchctl bootstrap gui/$(id -u)

After (cross-platform):
  brain init / npx brain-memory init
    → platform detect (darwin / linux / fallback)
    → SchedulerFactory.create(platform)
    → scheduler.install({ scriptPath: SLEEP_PASS_JS, dbPath, envFilePath })
    → writes env file (existing pattern, keep it)
    → prints hook snippet for settings.json
```

**New files — `src/scheduler/`:**

```
src/scheduler/
  index.ts          Scheduler interface + SchedulerFactory.create(platform)
  launchd.ts        macOS: renders plist template + launchctl bootstrap/bootout
  cron.ts           Linux: crontab -l | upsert | crontab -
  systemd-timer.ts  Linux: writes ~/.config/systemd/user/ unit + timer, systemctl --user enable
  node-cron.ts      Fallback: spawns a long-running node-cron wrapper process (all platforms)
  detect.ts         platform detection: process.platform + which(launchctl/systemctl/crontab)
```

Interface contract:
```typescript
export interface Scheduler {
  install(opts: SchedulerInstallOpts): Promise<void>;
  uninstall(): Promise<void>;
  status(): Promise<SchedulerStatus>;
}
export interface SchedulerInstallOpts {
  scriptPath: string;   // absolute path to compiled sleep-pass-cli.js (or ingest-cli.js)
  dbPath: string;
  envFilePath: string;  // the gitignored env file path
  intervalHours?: number; // default 1
}
export type SchedulerStatus = 'running' | 'stopped' | 'not_installed' | 'unknown';
```

**Platform detection logic (`detect.ts`):**
1. `process.platform === 'darwin'` AND `which launchctl` → LaunchdScheduler
2. `process.platform === 'linux'` AND `which systemctl` → SystemdTimerScheduler
3. `process.platform === 'linux'` AND `which crontab` → CronScheduler
4. Otherwise → NodeCronScheduler (fallback, no OS dependency)

**What does NOT change:** `sleep-pass-cli.ts`, `sleep-pass-launchd.sh`, the env file format, `BRAIN_MEMORY_*` env var names. The launchd path is preserved; new schedulers are additive.

**iMessage/watcher platform gating:** `watcher-cli.ts` already has the pattern — `config.channel.enable && config.channel.chatDbPath`. The init flow should add an explicit check: `process.platform !== 'darwin'` skips iMessage setup entirely and logs a platform notice. No code change needed in `watcher-cli.ts`; the config flag is sufficient.

**`brain doctor` — what it checks:**
- DB reachable + schema_version matches current SCHEMA_VERSION
- `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` valid (delegate to `DefaultModelProvider` — already exists in provider.ts)
- Scheduler registered and status === 'running' (via `scheduler.status()`)
- Hooks wired in `~/.claude/settings.json` (check file, grep for session-start-cli)
- iMessage/watcher only if `process.platform === 'darwin'`

### 2. Activation Trace

**What the code actually shows:**

`retrieveCueless()` in `RetrievalEngine` already has clear internal stages:
- Step 1 (lines 93–116): compute base scores for all live nodes
- Step 2 (lines 120–145): 1-hop spreading activation from top `SEED_K=10` seeds via `store.getOutEdges`; additive boost applied
- Step 3 (lines 148–152): re-rank all nodes by final score
- Step 4 (lines 155–179): hard_keep pin + token-budget fill

The trace emission points are exactly:
- After `seeds = sortedByBase.slice(0, SEED_K)` → emit seed events
- Inside the spreading activation loop (for each neighbor that gets boosted) → emit activated events

`recall()` in `RecallEngine` already has clear internal stages:
- After topk hit → emit schema_match event
- During neighborhood assembly loop → emit neighbor events

**Design: `ActivationTraceSink` (mirrors `ConsolidationSink` pattern exactly)**

New file: `src/traces/sink.ts`

```typescript
export type ActivationTraceEventType =
  | 'seed'         // top-K seed node (spreading activation start)
  | 'activated'    // node boosted by spreading activation (1-hop neighbor)
  | 'schema_match' // schema node resolved during recall
  | 'neighbor';    // 1-hop neighborhood node assembled during recall compose

export interface ActivationTraceEvent {
  trace_id: string;    // correlates all events for one retrieve/recall call
  event_type: ActivationTraceEventType;
  node_id: string;
  score: number;
  hop: number;         // 0 = seed/direct match, 1 = 1-hop neighbor
  source: 'retrieval' | 'recall';
}

export interface ActivationTraceSink {
  emit(event: ActivationTraceEvent): void;
}

// Production: writes to activation_trace table
export class SQLiteActivationTraceSink implements ActivationTraceSink { ... }

// Default: zero-overhead no-op (JIT eliminates dead code when enabled=false)
export class NoopActivationTraceSink implements ActivationTraceSink {
  emit(_event: ActivationTraceEvent): void {}
}

// Tests
export class MockActivationTraceSink implements ActivationTraceSink { ... }
```

**Schema change — `src/db/schema.ts`:**

Add `activation_trace` table (schema migration v3, same IF NOT EXISTS / ALTER pattern):

```sql
CREATE TABLE IF NOT EXISTS activation_trace (
  id        TEXT    PRIMARY KEY,
  ts        INTEGER NOT NULL,
  trace_id  TEXT    NOT NULL,
  event_type TEXT   NOT NULL,
  node_id   TEXT    NOT NULL,
  score     REAL    NOT NULL,
  hop       INTEGER NOT NULL DEFAULT 0,
  source    TEXT    NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_activation_trace_ts ON activation_trace(ts DESC);
CREATE INDEX IF NOT EXISTS idx_activation_trace_trace_id ON activation_trace(trace_id);
```

Ring-buffer: keep only last N traces. `SQLiteActivationTraceSink.emit()` runs a `DELETE WHERE id IN (SELECT id FROM activation_trace ORDER BY ts DESC LIMIT -1 OFFSET ?)` after insert (configurable, default 2000 events total).

**`RetrievalEngine` modification — minimal, additive:**

Constructor signature change:
```typescript
constructor(
  db: Database.Database,
  clock: Clock,
  config: EngineConfig,
  retriever: CandidateRetriever,
  store: SemanticStore,
  strength: StrengthDecayManager,
  gate: AllocationGate,
  traceSink: ActivationTraceSink = new NoopActivationTraceSink(), // NEW, last, optional
)
```

`retrieve(queryVec?, traceId?)` and `retrieveCueless(traceId?)` get an optional `traceId?: string`:

```typescript
// In Step 2 of retrieveCueless, after seeds computed:
if (traceId) {
  for (const [seedId, seedScore] of seeds) {
    this.traceSink.emit({ trace_id: traceId, event_type: 'seed', node_id: seedId, score: seedScore, hop: 0, source: 'retrieval' });
  }
}

// Inside the spreading activation loop, when boost is applied:
if (traceId) {
  this.traceSink.emit({ trace_id: traceId, event_type: 'activated', node_id: edge.dst, score: boost, hop: 1, source: 'retrieval' });
}
```

**Hot path protection**: `retrieveCueless()` is on the SessionStart hot path. The `traceId` is undefined during SessionStart (the hook doesn't pass one). The `NoopActivationTraceSink.emit()` is an empty method that the JIT inlines away. The `if (traceId)` guard also short-circuits before any sink call. Net impact: one extra undefined-check per seed (negligible, ~10 iterations of SEED_K).

**`RecallEngine` modification — same pattern:**

Constructor: add `traceSink: ActivationTraceSink = new NoopActivationTraceSink()` as the last parameter.

`recall(query, sessionId, traceId?)`: optional traceId, emits schema_match + neighbor events.

**Who generates traceIds:** Any caller that wants tracing passes a UUID. Candidates:
- `watcher-cli.ts` — per-tick, when a Telegram query comes in → generates traceId, passes to `responder.respond()` which threads it to `recall()`
- `recall-cli.ts` — for one-shot CLI recall queries
- `session-start-cli.ts` — explicitly does NOT pass traceId (preserve hot-path, no trace during SessionStart)

**`brain ui` live-tail:** the trace is stored in SQLite; the UI polls for new `activation_trace` rows since last seen timestamp.

### 3. Local Read-Only Web UI

**What the code enables:**

`SemanticStore` exposes `getNode(id)`, `getOutEdges(nodeId)`, `getInEdges(nodeId)` via prepared statements. These are read-only and exactly what a graph visualizer needs. WAL mode (already set) allows the UI server to open a second `Database` handle in read-only mode while the sleep pass writes.

The `consolidation_event` table is already a precedent for an append-only stream that a consumer reads. The new `activation_trace` table follows the same pattern.

**UI Server structure — `src/ui-server/`:**

```
src/ui-server/
  server.ts          Express + ws, opens DB readonly, mounts routes
  db-reader.ts       Lightweight read-only queries (NOT SemanticStore — avoids write methods)
  routes/
    graph.ts         GET /api/graph → { nodes, edges } snapshot
    traces.ts        GET /api/traces → list of trace_ids; GET /api/traces/:id → events
    stats.ts         GET /api/stats → node counts by type, tombstone ratio, edge count
  ws/
    live-tail.ts     WebSocket: polls activation_trace for rows newer than last seen ts
  public/            Bundled frontend (Vite output)
    index.html
    bundle.js
```

**`db-reader.ts` — read-only queries:**

Opens DB as `new Database(dbPath, { readonly: true })`. Never calls `initSchema` (read-only, cannot write). Prepared statements for:
- `SELECT id, type, value, s, c, tombstoned, last_access FROM node` (no embedding blob — UI doesn't need it, saves bandwidth)
- `SELECT src, dst, rel, w, kind FROM edge`
- `SELECT * FROM activation_trace WHERE ts > ? ORDER BY ts ASC LIMIT 500`
- `SELECT DISTINCT trace_id, MAX(ts) as latest FROM activation_trace GROUP BY trace_id ORDER BY latest DESC LIMIT 50`

**Frontend technology:**

Use `force-graph` npm package (canvas-based 2D force-directed graph, ~25KB gzipped, no React required, simple API). This avoids React build complexity while producing a visually compelling result. Bundled with Vite. Node visual encoding maps directly to `schema.ts` columns:
- Node color: type (entity=blue, fact=green, schema=purple, tombstoned=gray)
- Node size: `s` (strength) — stronger nodes are larger
- Node opacity: `c` (confidence)
- Edge thickness: `w` (edge weight)
- Edge style: kind (relation=solid, abstracts=dashed)

Animation: on a new trace replay, highlight nodes in sequence by event_type (seed=yellow pulse, activated=orange fade-in, schema_match=purple glow, neighbor=blue glow). CSS keyframe animation driven by event timing.

**Live-tail:** WebSocket handler in `ws/live-tail.ts` polls `activation_trace` at 1s intervals for rows newer than last seen `ts`. Pushes new events as JSON to connected clients. Clients animate them as they arrive.

**Static graph explorer mode:** no WebSocket, full graph snapshot loaded via `GET /api/graph`, rendered once. User can click nodes to see value, s, c, type. Toggle tombstoned nodes on/off.

**Entry point:** `brain ui [--port 7731]` — starts server, opens `http://localhost:7731` in browser. CLI lives at `src/adapter/brain-ui-cli.ts`.

**Honesty guard (SEED-002 load-bearing):** The UI copy says "memory activations" and "spreading activation pathways" — not "brain regions" or "cortex." The honesty guard lives in the frontend copy, not the server code. Document in a `ui-honesty.ts` constants file so the strings are auditable.

## Architectural Patterns

### Pattern 1: Optional Sink Injection (same as ConsolidationSink)

**What:** Constructor accepts a sink interface, defaults to a Noop implementation. Callers that want the behavior inject the real implementation; callers that don't inject nothing. The JIT eliminates dead Noop calls.

**When to use:** Any additive observability concern that must be strictly zero-overhead when disabled. This engine already uses it for ConsolidationSink. The ActivationTraceSink is the second application of the same pattern.

**Critical:** The sink parameter must be LAST in the constructor, optional, and default to Noop. All existing construction sites call the constructor positionally — adding a required parameter would break every call site. Adding it as a final optional preserves backward compatibility without requiring changes to the many files that construct these engines.

### Pattern 2: Read-Only DB Handle for Consumers

**What:** Consumers that only read (UI server, `brain doctor` DB check) open the DB as `new Database(dbPath, { readonly: true })`. This prevents accidental writes and is safe against WAL concurrent reads.

**When to use:** Any process that should never write the graph. The UI server is the primary case. `brain doctor` DB check is another.

**Do NOT reuse SemanticStore for read-only consumers.** SemanticStore carries write methods; handing it to the UI server creates an affordance for accidental writes. `db-reader.ts` is a clean read-only interface.

### Pattern 3: External Scheduler, Thin CLI Runner

**What:** The TS CLI runner (`sleep-pass-cli.ts`) is platform-agnostic and has no scheduler knowledge. Platform-specific registration lives in the scheduler seam. The env file is the bridge: the scheduler registers "run this wrapper script every hour," the wrapper sources the env file, the env file points to the TS CLI.

**When to use:** Any periodic job where platform portability matters. The existing launchd path is not changed — it becomes one implementation of the Scheduler interface.

## Anti-Patterns

### Anti-Pattern 1: Tracing the SessionStart Hot Path

**What people do:** Pass a traceId to `retrieveCueless()` from `session-start-cli.ts` so every inject is traced.

**Why it's wrong:** `session-start-cli.ts` blocks the user — it runs on every Claude Code session start. Adding a SQLite write (even a fast one) to the hot path violates the core latency constraint. The trace is for observability on explicit queries, not bulk injection.

**Do this instead:** Only pass traceId from `recall-cli.ts` and `watcher-cli.ts`. `session-start-cli.ts` always passes `undefined` — the `if (traceId)` guard short-circuits before any sink call.

### Anti-Pattern 2: Reusing SemanticStore in the UI Server

**What people do:** Import and instantiate `SemanticStore` in the UI server to read nodes and edges, because it already has `getNode`/`getOutEdges`/`getInEdges`.

**Why it's wrong:** SemanticStore carries `upsertNode`, `upsertEdge`, `tombstone`, `recordContradiction` — write methods with prepared statements that compile on construction. Giving these to the UI server creates an affordance for writes, violates the read-only intent, and imports the full write-path dependency into a process that should have none.

**Do this instead:** `db-reader.ts` with its own prepared statements, opened read-only. It shares the same SQL but carries no write surface.

### Anti-Pattern 3: Writing Trace Events Inside the Spreading Activation Transaction

**What people do:** Wrap the trace emit inside the same `db.transaction()` as a graph mutation.

**Why it's wrong:** The spreading activation in `retrieveCueless()` is not wrapped in any transaction (it's a read path). The trace write is a separate concern. Wrapping them together would add transaction overhead to a previously-transaction-free read path.

**Do this instead:** `SQLiteActivationTraceSink.emit()` runs its INSERT outside any transaction — it's a simple autocommit write to the `activation_trace` table. Acceptable because trace data is non-critical observability; losing one row on crash is fine.

### Anti-Pattern 4: Strengthening Inferred Episodes from Trace-Backed Queries

**What people do:** Because the UI can show which nodes lit up, it seems natural to strengthen those nodes (they were "accessed").

**Why it's wrong:** Traces record that nodes were activated by spreading activation, not that the user confirmed them. Strengthening on observation is the self-confirmation loop that the entire origin/provenance enforcement system exists to prevent. Traced activations are ephemeral observability data — they must never feed back into the graph as strengthening signals.

**Do this instead:** The activation_trace table is strictly append-only, read-only for the UI. No consolidation path reads from it. The sleep pass ignores it entirely.
