# Feature Research — v4.0 Proactive Memory

**Domain:** Proactive personal-assistant / proactive-memory for a self-hosted AI memory engine
**Researched:** 2026-06-15
**Confidence:** HIGH for HITL/Telegram patterns (official specs + real implementations found); MEDIUM for temporal ingestion specifics (Gmail episodic-variant is a product decision, not a solved problem); MEDIUM for surfacing heuristics (field is young, best-in-class behavior is consensus not spec)

---

## Context: What Exists vs. What's New

The research question is scoped to v4.0 additions only. Recense already ships:
- Salience scoring + PE-gated belief update (the "what deserves attention" signal)
- Schema induction + schema-prior recall
- Gmail/transcript/Obsidian ingestion via pluggable `SourceAdapter` seam
- Hourly sleep pass (existing scheduler, LLM-free hot path)
- stdio MCP + HTTP serve interfaces, pull-only Telegram reference client

The differentiator for v4.0 is that **recense's memory decides what's worth surfacing** — not a rule engine, not a schedule, but PE magnitude + salience + schema activation as the filter. Competitors (Lindy, Khoj, LangGraph-based agents) have the trigger/notify/approve plumbing; none have a memory substrate that learned what the user cares about and uses that to filter.

## Feature Area 1: Temporal/Actionable Ingestion

**What the feature does:** Captures time-anchored, action-relevant facts (deadlines, flights, receipts, RSVPs, follow-ups) that the current ingestion prompts explicitly discard. These are the prerequisite events that make proactive triggers possible — without them, the engine has no `event_at` or `due_at` to surface against.

### Table Stakes

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Gmail episodic-variant extraction prompt | The existing `GMAIL_EXTRACTION_PROMPT` explicitly ignores logistics ("scheduling logistics") — this is the deferred item #3 from `content-hardening-deferred.md`; without a separate prompt, zero temporal facts enter the graph | MEDIUM | Must be a **parallel prompt variant** (not a replacement) gated on email type/subject heuristic. Classify email as transactional/logistics vs. substantive before selecting prompt. The PE-gating and allocation gate remain — this just allows temporal claims through. Requires product sign-off (live DB risk). |
| `temporal` node property bag | Engine nodes have no `event_at`, `due_at`, or `fact_type` fields today; proactive triggering requires this metadata | MEDIUM | Add optional fields: `event_at: ISO8601`, `due_at: ISO8601`, `fact_type: flight\|deadline\|receipt\|followup\|rsvp\|event`, `is_completed: boolean`. These come from extraction, not inference. Store on the node; index `event_at` and `due_at` for fast range queries in the surfacing API. |
| Google Calendar `SourceAdapter` | Calendar is structured (iCal DTSTART/DTEND/RRULE/SUMMARY/ATTENDEES) — the most reliable source of temporal facts with zero extraction error; users expect "it knows my calendar" | HIGH | OAuth2 (same flow as Gmail). Adapter reads events via Google Calendar API v3, emits one episodic claim per event: `"<summary> on <date> at <time>"` plus temporal fields. Recurring events: emit next-occurrence only (avoid flooding). Cancellations: tombstone the existing node. This is a new SourceAdapter, not a prompt change. |
| Temporal extraction prompt for Gmail | A structured sub-prompt that, when the Gmail variant runs on a transactional email, extracts `{event_at, due_at, fact_type}` alongside the claim text | LOW | Works within existing extraction architecture. Instructs LLM: "If this claim is time-anchored, extract: event_at (ISO8601 or null), due_at (ISO8601 or null), fact_type (flight/deadline/receipt/followup/rsvp or null)." Returns alongside the claim in JSON. |

### Differentiators

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| PE-gated update when deadline changes | If a flight gets rescheduled, the old `event_at` surfaces a contradiction — PE magnitude triggers reconsolidation and updates the node in place. No other memory system does this | LOW (reuses existing PE machinery) | The existing three-way update already handles this. The differentiator is just that it works automatically — no special case needed. |
| Salience-gated temporal ingest (not everything enters) | Receipts from 6-month-ago purchases don't need to surface; the allocation gate already filters low-salience content | LOW (existing) | The existing `consolSkipThresholdBySource` controls this. The episodic-variant prompt doesn't bypass the gate. |
| TTL-by-category on temporal nodes | Flights with `event_at` in the past auto-mark `is_completed=true` on the next sleep pass; no manual cleanup | LOW | LLM-free: `SELECT * FROM nodes WHERE fact_type='flight' AND event_at < now() AND is_completed=0`. Run at sleep-pass start. Respects the "never delete evidence-backed fact" constraint — `is_completed` is a flag, not a delete. |

### Anti-Features

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Ingest ALL email with episodic variant | "More is better" intuition | Floods the graph with receipts, shipping confirmations, newsletter OTP codes; breaks PE-gating efficiency; live DB risk | Classify email type first (transactional heuristic on subject + sender domain), apply episodic variant only to classification=transactional; keep substantive-email prompt for threads |
| Parse iMessage history for temporal facts | Convenient source | Privacy violation risk, structural self-echo loop (same Apple ID), already rejected in Phase 7 (see auto-memory: imessage-channel-not-source) | Calendar + Gmail cover the structured sources; transcripts cover meetings |
| LLM-free temporal extraction from email | "Reduce cost" | Email date expressions are ambiguous ("next Thursday", "in two weeks", relative to reply date vs. send date) and require contextual resolution; rule-based NER fails on these | LLM extraction with structured output (cheap at D-cost models). The sleep pass already pays LLM cost. |

### Dependencies on Existing Recense Capabilities
- SourceAdapter seam (Phase 6) — plug in Calendar adapter
- Sleep-pass scheduler (hourly launchd) — temporal extraction runs in sleep pass
- PE-gated reconsolidation — handles deadline updates automatically
- Allocation gate — prevents low-salience temporal facts from entering

## Feature Area 2: Engine Surfacing Surface (LLM-Free Read API)

**What the feature does:** A thin, LLM-free API endpoint that answers "what should I push right now?" — ranking nodes by deadline proximity, salience, and novelty (PE-signal), filtered by seen/surfaced state. This is the internal decision layer; the Telegram client polls or the sleep pass pushes.

### Table Stakes

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| `GET /v1/surface` endpoint | The Telegram push client needs a way to ask "what's due/salient/new since last check?" — without this, the client has no signal | LOW | Returns ranked list of node IDs + surface reason + proposed message text. LLM-free: pure SQL over `event_at`, `salience_score`, `last_surfaced_at`, `is_completed`. |
| `surfaced_at` / `seen_at` state on nodes | Core dedup mechanism — without it, every poll re-surfaces the same facts | LOW | Add to node schema: `surfaced_at: ISO8601 \| null`, `seen_at: ISO8601 \| null`, `snoozed_until: ISO8601 \| null`. Set `surfaced_at` when the surfacing API returns a node; set `seen_at` when user dismisses/acts. |
| Multi-signal ranking (3 signals) | Single-signal ranking fails: deadline-only misses high-salience no-deadline items; salience-only misses urgent low-salience items | LOW | Composite score: `urgency = deadline_proximity_score * 0.6 + salience_score * 0.3 + pe_novelty_flag * 0.1`. Weights are configurable. Nodes with `is_completed=true` or `snoozed_until > now()` excluded. |
| Daily surface cap (default: 3 items/day) | Notification fatigue is the #1 failure mode for proactive assistants; without a cap, every sleep pass floods the user | LOW | Config param: `maxSurfacedPerDay: 3`. Tracked via `SELECT COUNT(*) FROM nodes WHERE DATE(surfaced_at) = DATE('now')`. P0 items (deadline within 24h) bypass the cap. |

### Differentiators

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| PE-novelty as a surfacing signal | If a belief was recently reconsolidated with high PE magnitude (something changed), it's a strong surfacing candidate — even without a deadline | LOW (uses existing PE metadata) | Track `last_pe_magnitude` on nodes (or in consolidation log). Surface if `last_pe_magnitude > threshold AND last_surfaced_at IS NULL` — "something changed in your memory that you haven't seen yet" |
| Schema-activation trigger | When the sleep pass induces a new schema or significantly expands an existing one, surface a synthesis ("I noticed a pattern: you consistently defer project X deadlines") | MEDIUM | Schema-level surfacing, not node-level. One surfacing per new/updated schema per week floor. Reuses SREL-01/02 machinery. |
| "Know when to stay silent" heuristic | The inverse: suppress if salience < floor AND no deadline AND no PE signal AND already surfaced within N days. Most facts qualify for silence. | LOW | Default suppress: `salience_score < 0.3 AND event_at IS NULL AND last_surfaced_at > (now - 7 days)`. This should fire for >80% of nodes on any given check — the engine should be mostly silent. |

### Anti-Features

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| LLM-based "what should I surface?" decision | Feels more intelligent | Adds latency + cost on every poll; violates the LLM-free online path constraint; LLM doesn't have a better signal than salience+PE anyway | Multi-signal SQL ranking is the right level of sophistication here; the differentiator comes from the quality of the memory, not an LLM scoring it |
| Real-time event-driven surfacing (webhook on every ingest) | Lower latency | Breaks the hourly sleep-pass model; online path must stay LLM-free; most temporal facts don't need sub-hour response | Hourly check is sufficient for deadlines (still surfaces 24h before) |
| Per-fact user priority configuration | "Let me mark this important" | Creates a configuration burden; the memory should learn priorities from behavior, not require explicit tagging | Trust salience + PE signal; add a "boost" callback from HITL dismiss/snooze feedback that adjusts `salience_score` (natural priority signal) |

### Dependencies on Existing Recense Capabilities
- `salience_score` on nodes (exists)
- PE magnitude from consolidation (exists, may need surfacing in node metadata)
- `brain serve` HTTP server (Phase 12) — the endpoint lives here
- Schema nodes and SREL edges (Phase 18) — for schema-activation trigger

## Feature Area 3: Notification + Digest UX

**What the feature does:** The actual delivery layer — how recense pushes salient/due items to the user, manages seen/snooze/dismiss state, and handles the difference between urgent one-offs and batched digests.

### Table Stakes

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Immediate push for P0 items (deadline < 24h) | Time-sensitive items need real-time delivery; a digest for a flight in 4 hours is useless | LOW | Telegram `sendMessage` on the push client's hourly poll. P0 = `event_at BETWEEN now() AND now() + 24h`. |
| Daily digest for P1 items (deadline 1–7 days out) | Prevents notification flood for non-urgent items; users expect to be able to check "what's coming up" without interruption | LOW | One digest message per day at configurable hour. Batches all P1 surfaceable items. If nothing to surface, no message (never send empty digests). |
| On-demand query ("what's coming up?") | Pull model from Phase 7 still works; the user can ask Telegram "what do I have this week?" | LOW (already exists via Telegram client) | Reuses existing `POST /v1/ask` endpoint; question routing detects temporal intent |
| Seen/dismiss state persisted | Re-surfacing a dismissed item is the second-fastest way to lose user trust (after too many notifications) | LOW | `seen_at` field set on dismiss. Snooze sets `snoozed_until`. Both exclude the item from `/v1/surface` response until cleared or expired. |
| Never send empty digests | Sending "nothing to report" trains users to ignore digests | LOW | Guard: `if (items.length === 0) return;` in the push client |

### Differentiators

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Feedback loop: snooze/dismiss adjusts salience | Dismissing a fact signals "this wasn't worth surfacing" → decrement salience slightly; approving/acting signals "this was valuable" → increment. The memory learns surfacing preferences over time. | MEDIUM | Requires a lightweight feedback write from the Telegram client back to `POST /v1/add` or a dedicated feedback endpoint. Must not violate D-43 (inferred content can't strengthen facts). Snooze/dismiss are user assertions, not inferences — safe. |
| Delivery channel prioritization (silent hours) | Don't push at 2am; respect user-configured quiet hours | LOW | Config: `quietHoursStart`, `quietHoursEnd`. P0 still fires (deadline emergency). P1 held until next active window. |

### Anti-Features

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Push notification to iOS/Android (native push) | "More reach" | Requires a hosted push notification server (APNs/FCM), defeating OSS self-host model; Telegram covers this without infrastructure | Telegram is the delivery channel; it sends phone notifications natively |
| Weekly digest (in addition to daily) | "Less noise" option | Doubles the UX complexity; weekly cadence loses temporal relevance for deadlines | Configurable daily quiet-hours cover this use case; the daily digest can be suppressed with `maxSurfacedPerDay: 0` for quiet days |
| Smart-reply drafting in digest | "Save me a step" | Drafting replies without a specific intent signal is speculative; most drafts go unused and erode trust | Surface the fact; if the user wants a reply drafted, they approve an action via HITL in Feature Area 4 |
| Read receipts / delivery confirmation | "Know if user saw it" | Telegram doesn't provide per-message read receipts in bot conversations; building a workaround (edit message with "seen" indicator) creates visual noise | Track `seen_at` from Telegram callback queries (button press = definitely seen) |

### Dependencies on Existing Recense Capabilities
- Telegram reference client (Phase 13) — extend push direction
- `brain serve` `/v1/surface` (new, from Feature Area 2)
- Hourly launchd scheduler (existing)

## Feature Area 4: Approval-Gated Action (HITL)

**What the feature does:** When the engine surfaces a salient item and there's a plausible action attached (send a follow-up, add a calendar block, mark a task done), the Telegram client proposes that action with an inline keyboard. The user approves, edits, rejects, or snoozes. Nothing fires without explicit approval. This is the "memory that acts" layer.

### Table Stakes

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Propose action with structured summary | The user cannot approve blindly; the proposal must show: what action, which tool/target, the exact parameters, and whether it's reversible | LOW | Telegram message format: `"Action: [verb] — [target]\nTool: [tool_name]\nParams: [key: value]\nReversible: yes/no\n[Approve] [Edit] [Reject] [Snooze]"` |
| Telegram inline keyboard (Approve / Edit / Reject / Snooze) | Standard Telegram HITL pattern (validated in the ecosystem: zeroclaw, Google ADK Telegram HITL examples) | LOW | Inline keyboard with `callback_data` prefix convention: `approve:<proposal_id>`, `reject:<proposal_id>`, `snooze:<proposal_id>`, `edit:<proposal_id>`. |
| Edit path: text input for parameter correction | "Approve as-is" fails when parameters are slightly wrong (wrong email address, wrong date); user must be able to correct before firing | MEDIUM | After "Edit" press: prompt user for the field to change via text reply. Parse reply, reconstruct the parameterized call, re-display proposal with changed params for final confirm. |
| Reject with optional reason | Rejection is learning data; capturing why a proposal was rejected helps tune surfacing/action selection | LOW | Optional: after "Reject", send follow-up "Why? (skip or reply)". Store reason in episodic log as an assertion (user-origin, not inferred) — feeds salience adjustment. |
| Audit log for all HITL decisions | Reproducibility + trust; user must be able to see what was proposed and what they decided | LOW | Append to episodic log: `{content: "User approved/rejected action X via Telegram", source: 'hitl', event_at: now(), action_proposal: JSON}`. Visible in `brain viz` node detail and via `brain ask`. |
| Snooze options (1h / tomorrow / dismiss forever) | Some proposals are right facts, wrong time; a single snooze duration creates friction | LOW | Three snooze options presented as a sub-keyboard after "Snooze": `[In 1 hour] [Tomorrow morning] [Never surface again]`. "Never" sets `snoozed_until = 9999-01-01` effectively. |
| Pending proposal timeout | If user doesn't respond within N hours, the proposal expires; don't queue stale actions | LOW | Proposals have a `expires_at`. On poll, skip expired proposals. Send a gentle timeout message if within quiet hours: "This proposal expired — trigger it again anytime by asking me." |

### Differentiators

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Proposal context from memory ("why I'm suggesting this") | Other HITL agents show what action they'll take; recense can show _why_ based on what it knows ("I noticed you have a deadline Thursday and haven't sent a follow-up since Monday") | LOW | Pull the 1-hop neighborhood of the surfaced node; generate a 1-sentence rationale from node content + schema. This is an LLM call — acceptable in the async push path. |
| Reversibility indicator on proposal | Users are more likely to approve when they know the action can be undone | LOW | `reversible: true` for calendar-add, task-status; `reversible: false` for send-email, post. Show prominently in proposal message. |
| Approval feeds back into salience | Acting on a proposal is strong evidence the item was worth surfacing → increment salience. Rejecting is evidence it wasn't → decrement. | MEDIUM | Same feedback loop as Feature Area 3 snooze/dismiss. A consistent reject pattern on a type of proposal should lower `maxSurfacedPerDay` for that type automatically. |

### Anti-Features

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Auto-approve after timeout | "I'm too busy to click Approve" | Violates the core HITL invariant; any auto-fire without approval is a trust-breaking event | Make proposals non-blocking; they sit in Telegram and the user acts on their schedule |
| Multiple pending proposals simultaneously | "Queue up all the actions" | Cognitive overload; user stops reading proposals; approval becomes rubber-stamping | Surface max 1 action proposal per Telegram message; batch non-urgent into digest section at the bottom |
| Approval via voice / NLP ("yes do it") | "More natural" | Parsing "yes" vs "yes but change the date" vs "yes to the first thing" is error-prone; inline keyboard is unambiguous | Telegram inline buttons are one tap and unambiguous; this is the right level of friction |
| Multi-step approval chains (approve → approve → approve) | Complex workflows | Breaks the single-approval UX contract; users lose track of where they are | Each proposal is atomic; complex workflows decompose into separate proposals surfaced sequentially |

### Dependencies on Existing Recense Capabilities
- Telegram reference client (Phase 13) — already handles message send/receive
- `brain serve` (Phase 12) — proposals route through HTTP endpoints
- Episodic log (Phase 1) — audit trail writes here
- Salience score (Phase 2) — feedback loop adjusts this

## Feature Area 5: Any-MCP Tool Execution

**What the feature does:** When a user approves a proposal, the Telegram client selects the appropriate MCP tool from connected servers, parameterizes it, and executes it. The approval from Feature Area 4 is the safety gate. The client must be able to handle _any_ MCP tool, not a hardcoded list.

### Table Stakes

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| MCP tool discovery (list_tools on connected servers) | The client needs to know what's available; without dynamic discovery, you have a hardcoded integration | LOW | On startup, call `list_tools` on each configured MCP server. Cache the schema (name, description, inputSchema). Refresh on reconnect. |
| LLM-mediated tool selection + parameterization | Given a surfaced intent ("follow up with Alice about the contract"), select the right tool (`send_email`) and fill params from memory context | MEDIUM | One LLM call (offline/async, not on hot path): `{intent, available_tools, memory_context} → {tool_name, params}`. This is where the LLM adds value — not in the approval decision. |
| Proposal formatting from selected tool+params | The approved/displayed format (Feature Area 4) is generated from this step | LOW | `{tool_name, params, description}` → human-readable Telegram message. |
| Execute on approval (not before) | The approval gate from Feature Area 4 is the invariant | LOW | After callback_data=`approve:<proposal_id>` received: look up proposal → call the MCP tool with stored params → log result → update `seen_at` on the surfaced node. |
| Execution result surfaced to user | User wants to know if it worked | LOW | After tool call returns: send Telegram message `"Done: [action summary]"` or `"Failed: [error]. Retry?"` |
| Per-server allowlist (not all tools on all servers) | User should control which MCP servers the push client can call | LOW | Config: `allowedMcpServers: [{url, allowedTools: ['send_email', 'add_event']}]`. Tool selection is restricted to allowlist. Prevents prompt injection via adversarial tool descriptions. |

### Differentiators

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Memory-grounded parameterization | The LLM selects params from retrieved memory context, not just from the surfaced fact alone. Example: "Alice's email" comes from a memory node, not just from the trigger event. | MEDIUM | During tool parameterization, perform a lightweight memory search (`/v1/search`) on the surfaced fact to pull related contact/entity nodes. Merge into the LLM's context window for parameterization. |
| MCP Elicitation for in-execution approval | When a tool execution mid-flight needs additional approval (e.g., the email draft is generated and needs review), MCP Elicitation (June 2025 spec) provides the native mechanism | HIGH (spec is draft; limited framework support) | Consider this v4.1 scope — MCP Elicitation was added to the spec June 2025 but has limited framework adoption. For v4.0, the Telegram HITL in Feature Area 4 covers the pre-execution approval. |

### Anti-Features

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Tool injection from untrusted MCP servers | "More tools = more capability" | Adversarial tool descriptions (prompt injection via metadata) can manipulate tool selection; MCP security research (arxiv 2508.12538) identifies this as the primary attack vector | Per-server allowlist (above) is the mitigation; never auto-discover tools from unverified servers |
| LLM selects the approval threshold (should we approve this?) | "Smart filtering" | LLMs are inconsistent gatekeepers; approval decision must be human, not model | LLM selects+parameterizes; human approves. The two roles don't swap. |
| Build a custom MCP server registry / tool marketplace | "More integrations" | This is commodity infrastructure; the engine's value is in what it surfaces, not in which tools it can call | Users configure their own MCP servers (calendar MCP, email MCP, task MCP); the client works with anything that speaks the protocol |
| Chained tool calls without intermediate approval | "Complete the workflow end to end" | Each tool call is consequential; chaining without approval removes the HITL guarantee | Each consequential step requires its own proposal. The UX cost of sequential approvals is the intentional friction. |

### Dependencies on Existing Recense Capabilities
- `brain serve` HTTP API (Phase 12) — client calls `/v1/search` for memory-grounded parameterization
- stdio MCP server (Phase 11) — recense itself is a tool; the push client may call it
- Telegram reference client (Phase 13) — execution and result delivery
- HITL approval from Feature Area 4 — the gate

### Dependency Notes

- **Gmail episodic-variant requires product decision**: this touches live ingestion behavior on the production DB. Must be gated behind a runtime flag (`RECENSE_ENABLE_EPISODIC_EMAIL=false` by default) and validated on a sample before enabling. See deferred item #3 in `content-hardening-deferred.md`.
- **Calendar adapter requires OAuth2 plumbing**: same pattern as Gmail (Phase 6), but Calendar is a separate OAuth scope. Can reuse the OAuth flow; cannot reuse the Gmail token.
- **`/v1/surface` endpoint requires schema migration**: adding `surfaced_at`, `seen_at`, `snoozed_until`, `event_at`, `due_at`, `fact_type`, `is_completed` to the node table is a breaking schema change (v8→v9). Must run at `brain init` and be idempotent.
- **MCP tool execution requires the push client to hold MCP client state**: the Telegram reference client (Phase 13) currently only calls the HTTP serve API; extending it to act as an MCP client for external tool servers is a larger architectural addition.

### Future Consideration (v5+)

- [ ] Multiple delivery channels (email digest, Slack) — Telegram covers the self-host use case; other channels are distribution decisions
- [ ] Per-schema surfacing frequency tuning — needs several months of usage data
- [ ] Learning surfacing preferences from behavior patterns (RL-style) — requires Phase 17+ eval data

## Notification Fatigue: First-Class Treatment

Notification fatigue is the #1 failure mode for proactive assistants (research consensus: Courier 2026, IBM alert-fatigue, arxiv 2003.02097). The design must make silence the default state, not an exception.

**The "stay silent" heuristic (suppress unless at least one of these is true):**
1. `event_at BETWEEN now() AND now() + 24h` (P0: imminent deadline)
2. `due_at BETWEEN now() AND now() + 7d AND surfaced_at IS NULL` (P1: upcoming, unseen)
3. `last_pe_magnitude > 0.5 AND surfaced_at IS NULL` (high-novelty belief change, never surfaced)
4. `schema_activated_this_pass = true AND last_schema_surface > 7 days ago` (new pattern, weekly cap)

**Everything else stays silent.** The default for any given node on any given day should be silence.

**Layered fatigue guards (additive):**
- Daily cap: default 3 items/day (P0 bypass)
- Seen-state dedup: never re-surface until snoozed or expired
- Quiet hours: configurable suppress window
- Empty-digest suppression: never send a push with no content

## Competitor Feature Comparison

| Feature | Lindy | Khoj | LangGraph HITL | Recense v4.0 |
|---------|-------|------|----------------|--------------|
| Proactive Telegram push | Yes (workflow-triggered) | Partial (WhatsApp/web) | No (framework only) | Yes (memory-driven) |
| Temporal ingestion (calendar) | Yes (via integrations) | Partial | No | Yes (SourceAdapter) |
| Surfacing filter | Rule-based / schedule | Query-based | External logic | PE + salience + schema |
| HITL approval | Yes (workflow-level) | No | Yes (interrupt()) | Yes (Telegram inline) |
| Any-MCP tool execution | No (Lindy tools only) | No | No | Yes (with allowlist) |
| Self-hosted / BYO-keys | No | Yes | Yes (framework) | Yes |
| Memory learns surfacing preference | No | No | No | Yes (via salience feedback) |

The table shows the core claim: Lindy/Khoj have the plumbing but not the memory-driven filter. LangGraph has the HITL pattern but not the delivery or the memory. Recense v4.0 is the only combination of memory-grounded surfacing + HITL + any-MCP at self-hosted scale.
