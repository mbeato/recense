# Stack Research

**Project:** brain-memory v2.0 Open-Source Release
**Researched:** 2026-06-09
**Existing stack baseline:** TypeScript / Node.js >=22 / better-sqlite3 ^12.10.0 / @anthropic-ai/sdk / openai / macOS launchd (scheduler) / no CLI framework / no web server
**Confidence:** HIGH across all areas (npm registry + official docs verified)

---

## Area A: OSS Install/DX + CLI Bootstrap + Doctor

### Recommended additions

| Library | Version | Purpose | Why |
|---------|---------|---------|-----|
| `commander` | `^15.0.0` | CLI framework (`brain init`, `brain doctor`, `brain viz`, `brain daemon`) | Zero runtime deps, bundles its own TS types, subcommand tree, auto-generated help. `bin` field wires `brain` → `dist/src/cli.js`. |
| `@clack/prompts` | `^1.5.1` | Interactive guided prompts for `init` | Beautiful TUI (`text()`, `confirm()`, `spinner()`, `select()`). Four JS-only deps, no native addons. Used by Astro/Vite/SvelteKit scaffolders. Fits "Enter your key → validating…". |
| `picocolors` | `^1.1.1` | Terminal colors for `brain doctor` | Zero deps, **CJS-native** — critical because tsconfig compiles to CommonJS and chalk 5 is ESM-only (breaks at runtime). |

### What NOT to add

| Avoid | Why |
|-------|-----|
| `chalk ^5` | ESM-only; project compiles to CJS — `require('chalk')` throws at runtime |
| `inquirer` | Heavier than `@clack/prompts`, more deps, older DX |
| `oclif` | Framework overkill — scaffolds a whole plugin system |
| `yargs` | More complex/heavier than commander for this use case |
| Key-rotation / secrets-manager libs | Key validation goes through the existing `ModelProvider` seam — no new dep |

### Integration pattern

`package.json` gains `bin: { "brain": "dist/src/cli.js" }` + a `files` field. `brain init` (commander subcommand) uses `@clack/prompts` to collect DB path + API keys, writes `~/.config/brain-memory/sleep.env` (existing env-file pattern), validates keys through the existing `ModelProvider` seam.

## Area B: Cross-Platform Scheduler Seam

### Recommended addition

| Library | Version | Purpose | Why |
|---------|---------|---------|-----|
| `croner` | `^10.0.1` | In-process cron scheduler for a universal `CronerBackend` | Zero deps, bundles TS types, Node >=18, DST/timezone via built-in `Intl` (node-cron historically breaks on DST). `catch` option keeps sleep-pass errors from crashing the daemon. More actively maintained than node-cron (v10 vs v4). |

### Architecture for the scheduler seam

```
SchedulerBackend
  LaunchdBackend   (macOS, existing plist/launchctl wiring — unchanged)
  CronerBackend    (universal: croner runs the sleep pass hourly in-process)
```

`brain init` detects `process.platform`: `darwin` → launchd default (croner fallback); `linux`/`win32` → croner daemon. `brain daemon start|stop|status` manages the persistent croner process via a PID file in `~/.config/brain-memory/daemon.pid`. Avoids systemd-unit / Windows-Task-Scheduler registration complexity — one cross-platform pattern covers Linux + Windows for v2.0.

> **Note (open question from Architecture research):** a long-running croner daemon may itself need launchd/systemd to survive reboots on headless servers — partially defeating the "fallback" purpose. Scope the fallback to developer machines for v2.0; headless-server reboot-survival is a later concern.

### What NOT to add

| Avoid | Why |
|-------|-----|
| `node-cron ^4` | Weaker TS types and worse DST handling than croner — no advantage |
| `node-schedule ^2` | 3 transitive deps for equivalent functionality |
| `bull` / `agenda` / `bree` | Redis/MongoDB deps — wrong scale for a single-user daemon |
| systemd-unit registration libs | Too complex/fragile across distros |

## Area C: Brain-Activation Visualization

### Recommended addition

| Library | Version | Purpose | Why |
|---------|---------|---------|-----|
| `force-graph` | `^1.51.4` | Canvas force-directed graph + animation | 15 JS-only deps (no native addons). Canvas (no WebGL). Right scale for brain-memory (100–5000 nodes). Ships a UMD bundle servable directly from `node_modules` — no bundler. Built-in physics + tweenjs makes "node light up" a ~2-line call. |

### Zero new deps for the server layer

`brain viz` HTTP server uses **`node:http` (built-in)** only. Routes:
- `GET /` → inline HTML with `<script src="/force-graph.min.js">`
- `GET /force-graph.min.js` → pipe the UMD file (`require.resolve('force-graph/dist/force-graph.min.js')`)
- `GET /api/graph` → JSON snapshot read from a **read-only** SQLite connection
- `GET /api/activations` → SSE stream of activation-trace events

Browser auto-open via `child_process.exec` with platform detection (`open`/`xdg-open`/`start`) — zero deps.

### Activation trace integration points (per SEED-002)

- `src/retrieval/engine.ts` (`RetrievalEngine`) — seed selection + 1-hop spread
- `src/recall/index.ts` (`RecallEngine`) — schema-neighborhood traversal

Trace is an optional sink/callback, **off by default** (hot path unchanged). When `brain viz` runs, the server registers it and pushes SSE events.

### What NOT to add

| Avoid | Why |
|-------|-----|
| `react` / `react-force-graph` | React adds ~40MB install + a bundler step for a read-only local UI — massive friction |
| `three.js` | 3D overkill; heavier build; spreading activation is inherently 2D |
| `sigma ^3` | Needs `graphology` peer dep; WebGL overkill at <5000 nodes |
| `cytoscape ^3` | More verbose animation API than force-graph for the "light up" effect |
| `express` / `fastify` | A 3-route read-only server doesn't need a framework; `node:http` is ~50 lines |
| `esbuild`/`vite`/`webpack` at runtime | No bundler needed — force-graph UMD served from node_modules |
| `open ^10` (npm) | ESM-only; project is CJS — use `child_process.exec` + platform detection |

> **Frontend note:** the Architecture researcher flagged `force-graph` (vanilla, canvas, ~25KB, no React) vs `react-force-graph` (heavier, more composable) as an open decision. STACK recommends **vanilla `force-graph`** to keep install friction minimal and avoid a bundler — aligns with the no-React stance above.
