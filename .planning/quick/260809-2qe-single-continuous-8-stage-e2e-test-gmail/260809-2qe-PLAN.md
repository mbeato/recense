<design_pins>
These five decisions were established from live source during planning. They are the failure modes that
would otherwise burn a debugging cycle each. Do not re-litigate them; implement them.

**P-1 — File-backed temp DB, never `:memory:`.**
`createBrainHttpServer` takes a `dbPath` and opens its OWN handles. The consolidation half must therefore
write to the same temp FILE. Use `proposal-reference-e2e.test.ts`'s `makeTempDbPath` / `getFreePort` /
`RECENSE_LOCK_PATH` setup verbatim.

**P-2 — `new FakeClock(Date.now())`, NOT `FakeClock(Date.UTC(2026, 0, 1))`.**
This is the single highest-risk silent failure in the whole file. `SQLiteActionProposalSink` stamps
`expires_at = clock.nowMs() + PROPOSAL_TTL_MS` (14 days), and the server's store filters `expires_at > now`
against `realClock`. Seeding the customary 2026-01-01 fake clock makes every emitted proposal already
expired at list time, so `GET /v1/proposals` returns an empty array and stage 7-8 silently proves nothing.
Seed the FakeClock at real `Date.now()` — determinism within the run is preserved (the clock never advances),
and the TTL window stays open. Put this reasoning in a comment at the construction site.

**P-3 — Stock (dark) `provenanceDistinctnessEnabled`.**
`DEFAULT_CONFIG.provenanceDistinctnessEnabled` is `false` pending the founder gate. This file must exercise
the chain that SHIPS, so leave the knob alone and assert `episode.session_id === COLLAPSED_GMAIL_PROVENANCE_KEY`.
The derived key is still computed unconditionally inside `normalizeGmailMessage` (D-14 dark-launch semantics),
so the derivation is exercised either way, and the enabled-path behavior is already proven in
`drift-belief-correction-e2e.test.ts`. Consequence: the decisive recipe must NOT depend on
distinct-provenance counting (see P-4).

**P-4 — Decisive recipe: one contradiction at magnitude 0.06, routing to `contradict_reconcile`.**
A freshly minted node has s=0.1, c=0.5 -> resistance ~0.05. magnitude 0.06 gives ratio 1.2, inside
[`peReconcileBandLow` 0.8, `peReconcileBandHigh` 2.0) -> mid-band reconcile: old node tombstoned, new node
minted carrying `prev_value`, event type `contradict_reconcile`, which `isEmissionEligible` accepts.
Precedent: the "discriminates on time, not content" case in `drift-belief-correction-e2e.test.ts` and the
oscillation fixture in `action-proposal-emission.test.ts`. Do NOT reach for the three-distinct-provenance
force-destabilize recipe (magnitude 0.03 x3) — it requires the dark knob from P-3.

**P-5 — Two pulls, two `consolidate()` passes.**
Script the fake fetcher to return batch 1 (the mint email) on the first `fetchMessages` call and batch 2
(the contradicting email) on the second, and run `runPullPhase` -> `consolidate()` for each. This mirrors
production (two sleep passes), sidesteps intra-pass episode-ordering questions entirely (the discipline
`drift-belief-correction-e2e.test.ts` documents for its own fixtures), and genuinely exercises the
`cursor:gmail:default` seam — first pull has `cursor === null` (backfill ordering branch), second pull
carries the committed historyId (incremental branch).
