# Phase 999.3 Plan 01: Scope-aware Provenance Engine Layer Summary

Single-tenant **provenance** scope on consolidated facts via a sparse `node_scope` sidecar (schema v10), a pure `cwd → scope` derivation, consolidation-time stamping from contributing-episode cwd, and display-only scope surfacing in ambient recall — with retrieval ranking provably untouched (D-S1).

### Design highlights

- **Faithfulness (D-S2):** scope lives in a NEW sparse sidecar `node_scope (node_id PK FK→node.id, scope NOT NULL, updated_at NOT NULL)`, mirroring `node_temporal` exactly — `CREATE TABLE IF NOT EXISTS`, additive, no `ALTER TABLE node`, no `BEGIN/COMMIT` wrap. The `node` table stays the pure belief record. Confirmed via a test asserting `node` has no `scope` column.
- **Provenance not tenancy (D-S1):** `stampNodeScopes` runs **after** `consolidator.consolidate()` and recall reads scope **after** `retrieveRanked`. `consolidator.ts` was not touched at all, so belief logic (values, dedup, tombstoning, judge) is byte-for-byte unchanged. A dedicated Task-5 test strips the `[slug]` markers from the scoped recall output and asserts it equals the no-scope baseline line-for-line.
- **Best-effort write (Task 4):** the entire `stampNodeScopes` body is wrapped in `try/catch`; a scope-write error can never abort or alter the belief write.
- **Multi-project resolution (D-S3):** scope is resolved from the DISTINCT cwd of ALL a node's contributing episodes via the `consolidation_event → episode` join, so a node confirmed by episodes from two projects collapses to `global`.
- **Net-zero new runtime dependencies:** TS + SQL only.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Stale `SCHEMA_VERSION === 9` literal assertions broke after the version bump**
- **Found during:** Task 1 (and full-suite regression check)
- **Issue:** Five pre-existing tests hardcoded the literal `9`/`'9'` for SCHEMA_VERSION instead of comparing dynamically: `tests/node-temporal-schema.test.ts`, `tests/activation-sink.test.ts` (×2), `tests/schema.test.ts`, `tests/surfaced-event-schema.test.ts`. Bumping to 10 per the plan necessarily fails these.
- **Fix:** Updated each literal assertion 9 → 10. In-scope because the version bump (mandated by the plan) directly causes the failures.
- **Commits:** `a132b21`, `346093c`

**2. [Rule 3 - Blocking] `dist/` rebuild required for build-dependent CLI tests**
- **Found during:** full-suite regression check
- **Issue:** `tests/adapter-inject.test.ts` spawns the compiled `dist/src/adapter/session-start-cli.js`, which had `SCHEMA_VERSION=9` baked into the stale build. With fresh DBs now stamped v10, the compiled CLI's version-match guard rejected them and emitted empty context.
- **Fix:** `npm run build` to regenerate dist at v10 (also the repo's `pretest` step). No source change — expected consequence of any schema bump.

### Design choice vs. plan file list

- The plan's Task 4 `files_modified` listed `src/consolidation/run-sleep-pass.ts`, and its `read_first` pointed there for "where nodes are upserted." The actual per-node upsert + sidecar stamping happens in `src/consolidation/consolidator.ts` (default sink is a no-op). The post-pass `stampNodeScopes` approach in `run-sleep-pass.ts` was chosen precisely because it matches the planned file AND keeps `consolidator.ts` untouched, which is the strongest possible guarantee that belief consolidation is unchanged. No deviation from the plan's intent — `consolidator.ts` was intentionally not modified.
