# Phase 61 — UI Design Contract

> Visual and interaction contract for the corpus index-column restructure + project-browsing
> focus flow. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> This is a **vanilla JS/CSS canvas+DOM viz** (no React/shadcn/component framework) — the
> shadcn gate does not apply. All values below are pre-populated from the live codebase
> (`src/viz/modules/constants.js`, `src/viz/css/styles.css`) and the 61-CONTEXT.md /
> 59-CONTEXT.md / 57-CONTEXT.md locked decisions. This phase EXTENDS an established design
> system — it does not invent one; deviations from a textbook token scale are called out
> explicitly where they match existing, unchanged codebase convention (surgical-diff rule).

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `var(--bg-scene)` `#170f1d` | Scene/corpus canvas background (unchanged, global) |
| Secondary (30%) | `var(--glass-bg-focused)` `rgba(26,18,32,0.90)` for `#index-panel`; `var(--glass-bg-ambient)` `rgba(26,18,32,0.66)` for `#index-reopen` | D-02/D-08 glass reskin — see rationale below |
| Accent (10%) | `var(--accent-amber-solid)` `#d9a05c` (+ `accent-amber-tint*` variants) | **Reserved EXCLUSIVELY for:** (a) graph-node/link hover-subtree highlight (existing `HOVER_NODE`/`highlightCorpusNode` mechanism in corpus.js, unchanged), (b) the new graph-hover parity this phase adds (D-05, same mechanism, keyed off `onNodeHover` instead of only index-row hover). Amber must NEVER appear on: chevron icons, count badges, tree-row backgrounds/text, the focused-project's node fill (see Focus vs. Hover below), or any new CSS this phase adds. |
| Destructive | not applicable | No destructive actions in this phase (D-07 deletes a UI element — a fixed button — not user data; no confirmation copy needed) |

**Glass-tier rationale (Claude's Discretion, D-02/D-08):** `#index-panel` is a large persistent
content panel — pair it with the same "focused" tier already used by `#detail`/`#settings-panel`/
`#reader` (`glass-bg-focused` + `glass-blur-md` 14px + `glass-border-focused` + `radius-lg`),
NOT the smaller "ambient" tier used by the floating `#hud-rail`. `#index-reopen` is a small
floating icon affordance (30x30, same species as `#hud-rail`) — pair it with the "ambient" tier
(`glass-bg-ambient` + `glass-blur-sm` 8px + `glass-border` + `radius-md`), matching `#hud-rail`'s
own container recipe (styles.css:195-213), not its transparent inner buttons.

**Focus vs. Hover (load-bearing distinction, D-04 vs D-05):** hovering a node/row is momentary
and amber (existing convention). Focusing a project (D-03/D-04 click) is persistent and must
NOT recolor the focused project's nodes amber — amber is activation/hover-only project-wide
(57-CONTEXT D-03(b), machine-locked). Focus is expressed by **dimming everything else** (opacity
drop on non-related nodes/links, reusing the existing `scopeColor(scope)` fill for the focused
set unchanged) — never by brightening the focused set into a new hue.

## Interaction Contract

(Supplementary to the standard template — captures the structural/behavioral contract the
planner and executor need; not a standard UI-SPEC section but required for this phase to be
implementable without ambiguity.)

### Tree structure (D-01)
- Default state: **every project row starts collapsed** (chevron ▶ + name + count badge).
  Doc rows are NOT rendered until expanded.
- Multiple projects may be expanded simultaneously — no accordion/single-open constraint
  (Claude's Discretion default; flag for founder checkpoint if this reads wrong live).
- Existing `index-content` build already computes a parent/child tree from `parentId` — reuse
  this data shape; the only change is gating child `<li>` rendering behind an `expanded` Set,
  not rendering everything flat-with-indent as today.
- Filter behavior (existing `computeVisible`, index.js:142-154) already auto-includes ancestors
  of a match — extend it to also force-expand any collapsed ancestor of a match while a filter
  is active (CONTEXT.md discretion item: "filtering should auto-expand matching branches").
  Clearing the filter should NOT auto-collapse rows the user manually expanded.
- Whether expand state persists across corpus close/reopen within a session: default to
  **persist in-memory only** (not localStorage) — resets on a hard page reload, survives a
  corpus→brain→corpus round-trip within the same session. Flag as discretionary if this reads
  wrong at the founder checkpoint.

### Row click targets (D-03)
- Chevron (own hit target, ~20x20px minimum) → toggle expand/collapse ONLY.
- Project name text (the rest of the row) → `focusCorpusProject(scope)` (new hook) — zooms/
  brightens that project's cluster, dims others, AND expands its tree row (D-03: click both
  focuses AND expands — one click does both, not two separate affordances).
- Doc rows (leaf entries) → unchanged: `ctx.openReader(slug, {from:'corpus'})`.
- Hover (any row) → unchanged: `ctx.highlightCorpusNode(slug)` amber subtree highlight in the
  graph (existing mechanism, D-05 extends the SAME mechanism to graph-side node hover).

### Focus flow (D-04)
- Enter: click a project name (index row OR, per D-05, directly on its hub node in the graph).
- While focused: non-project nodes/links fade to a low dim opacity (new named constant — see
  Tunables below); the focused project's nodes render at full/normal opacity+color (no amber).
  Camera zooms/frames to the focused cluster (reuse `zoomToFit`/`fitAndClamp` pattern already
  used by `refitCorpus`).
- Exit: click empty canvas, press Esc, or click a different project (switches focus directly,
  no need to exit-then-reenter). No back button, no other chrome.
- Esc ownership: this phase's Esc handler must coexist with the existing reader/palette Esc
  owner (59-CONTEXT: "one owner for the shortcut map") — do not add a second competing listener;
  extend the existing shortcut dispatch with a focus-exit branch, checked after
  reader/palette-open state (so Esc closes the topmost/most-specific UI first).
- Reader round-trip interaction with focus (discretionary, CONTEXT.md suggests): focus SHOULD
  persist across `openReader` → `returnToCorpus` (D4 flow itself must not regress — verify no
  behavior change to the existing reader round-trip contract).

### Graph hover parity (D-05)
- Hovering a node directly in `#corpus-graph` must call the SAME `highlightCorpusNode(slug)`
  BFS-subtree-then-amber mechanism the index row hover already uses (corpus.js:628-660) — reuse,
  don't reimplement.
- Additionally: while any node is hovered OR any project is focused, non-related nodes should
  dim (new behavior — today `onNodeHover`, corpus.js:339-342, only sets cursor + `hoveredId`,
  it does NOT dim). This is the fix for the founder's "flat" hover complaint (D3).

### Tiered labels (D-06)
- Today `nodeCanvasObject` (corpus.js:248-278) draws EVERY node's label unconditionally at
  every zoom level — this is the root cause of the "labels on top of each other" defect (D3).
- New tiering (project hub = root scope node; subject doc = mid-tier; chapter doc = UUID-slug
  leaf, already alpha-dimmed 0.35 per D-13):
  - Project hub labels: always visible (unchanged from today for hubs specifically).
  - Subject-doc labels: visible only past a zoom-in threshold (new named constant) OR when
    their parent project is focused/hovered.
  - Chapter-doc labels: visible only on direct hover of that specific node (never at rest,
    never just from project-focus — matches D-07's "chapters appear exactly when browsing").
- Chapter node/link visibility itself moves from the deleted toggle button to focus-driven
  (see D-07 below) — tiered LABELS are a separate, additional gate on top of that.

### Chapter visibility (D-07)
- Delete `#btn-corpus-chapters` and the `showChapters` boolean entirely (corpus.js:131,143-172).
- Chapter docs (`isChapterNode`/UUID-slug test, already used by `isNodeVisible`) become visible
  via `nodeVisibility`/`linkVisibility` exactly when their parent project is **focused** or its
  index tree row is **expanded** — reuse the existing `nodeVisibility`/`linkVisibility` reassert
  pattern (corpus.js:289-295, "instant toggle, positions stay pinned").

## Named Tunables To Add (`src/viz/modules/constants.js`)

Per the Phase-57 D-10 single-source-of-truth rule — every new feel value is a named constant,
not an inline literal, tuned live at the closing founder checkpoint (CONTEXT.md discretion):

| Constant (suggested name) | Purpose | Provisional starting value |
|---|---|---|
| `CORPUS_FOCUS_DIM_OPACITY` | Non-focused-project node/link opacity while a project is focused | ~0.15-0.20 (gentler than the 3D `FOCUS_DIM_OPACITY` 0.035 — 2D context nodes should stay legibly present, not near-invisible) |
| `CORPUS_HOVER_DIM_OPACITY` | Non-related node/link opacity while hovering a node (D-05) | ~0.25-0.35 (a lighter recede than sustained focus, since hover is momentary) |
| `CORPUS_LABEL_ZOOM_THRESHOLD` | Zoom level past which subject-doc labels fade in (D-06) | pick relative to the existing `fitAndClamp`/`MAX_ZOOM` clamp range — provisional, tune at checkpoint |
| `CORPUS_FOCUS_TRANSITION_MS` | Camera zoom/frame duration entering/exiting focus | ~400-600ms (matches the existing `--motion-slow` 220ms family scaled up for a camera move, not a UI fade — reference `SETTLE_BUDGET_MS`/existing corpus fade `380ms` as sibling values) |

These join `HUD_CSS_TOKENS`/motion tokens already in `constants.js` — do not declare a second
constants module or inline these in corpus.js/index.js.
