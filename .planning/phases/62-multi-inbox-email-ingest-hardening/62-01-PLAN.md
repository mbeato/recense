<objective>
Give each configured Google account its own Gmail query for its initial backfill, through a real
user-facing configuration surface, and make the backfill-only nature of that scoping honest and
visible instead of implied away.

Purpose: EMAIL-02. Today `config.googleAccounts` is a compile-time literal — `ingest-cli.ts` builds
its config as `{ ...DEFAULT_CONFIG, dbPath, dirtySentinelPath, enabledSources }` and never overrides
`googleAccounts`, so a second account is unreachable without editing source. And `config.gmail.query`
is global. Both gaps must close before any onboarding flow (plan 62-02) has anywhere to register an
account. Per the locked decision, scoping is accepted as backfill-only: `users.history.list` accepts
no `q` parameter, so incremental pulls are unfiltered and lean on the existing gmail source weight
(0.35) + skip threshold (0.4) dampening. This plan makes that limitation stated, not worked around.

Output: `resolveGoogleAccounts()` in runtime-config, an optional `query` on each `googleAccounts`
entry, per-account query resolution in `GmailAdapter.pull()`, a ninth `recense doctor` dimension,
and a regression test locking in that the incremental branch carries no `q`.
</objective>

- `resolveGoogleAccounts(env?: NodeJS.ProcessEnv): Array<{ id: string; query?: string }>` in `src/adapter/runtime-config.ts`

- `checkGmailAccounts(envPath?: string): CheckResult` in `src/adapter/recense-doctor.ts`

Account-id charset (shared with plan 62-02): `/^[a-z][a-z0-9_]{0,31}$/`. Lowercase-only so the
uppercase env-key derivation is unambiguous; no commas, `=`, or newlines so an id can never break
either the comma-separated list or the `KEY=VALUE` env-file grammar.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sleep.env file → process | Operator-authored config crosses into `googleAccounts` ids and query strings. Ids are used to derive env-var key names and a comma-separated list; a malformed id could break the env grammar or the account list. |
| process → stdout (`recense doctor`) | The doctor's detail strings are printed to a terminal and routinely pasted into issues/chats. Refresh tokens and client secrets live in the same env file being read. |
| Gmail API → adapter | Message content is untrusted; account ids are NOT — they come from trusted config, never from email content (existing T-20-06). This plan must not weaken that. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-62-01 | Tampering | `resolveGoogleAccounts` id parsing | mitigate | Enforce `/^[a-z][a-z0-9_]{0,31}$/` per id and silently drop non-conforming ids. Rejects commas, `=`, newlines, and whitespace, so a crafted id cannot inject a second entry into `RECENSE_GOOGLE_ACCOUNTS` or a bogus `KEY=VALUE` line into the env grammar. Test asserts each of those shapes is dropped. |
| T-62-02 | Denial of Service | `resolveGoogleAccounts` fail posture | mitigate | Never throw. An empty, malformed, or wholly-invalid var falls back to `[{ id: 'default' }]`, matching `resolveEnabledSources` posture, so a bad config degrades to today's single-account behaviour instead of killing the ingest run. Test asserts no-throw across all malformed inputs. |
| T-62-03 | Information Disclosure | `resolveAccountQuery` / adapter logs | mitigate | The resolved query is passed only to `fetchMessages`; it is never logged. Existing adapter logging already logs only `adapter.source` and the error string (T-06-25) and is untouched. |
| T-62-04 | Information Disclosure | `checkGmailAccounts` stdout | mitigate | Report presence booleans and query PROVENANCE (`per-account` vs `global default`) only. Never interpolate a refresh token, client secret, or query string into the detail. Enforced by a test that plants a sentinel token value and a sentinel query value and asserts neither appears in `result.detail`. |
| T-62-05 | Repudiation | Silent per-account credential death (Pitfall 16.2) | mitigate | `checkGmailAccounts` returns `fail` when an enabled account lacks its refresh token, surfacing a revoked account-2 grant that today only produces one line in `/tmp/recense-ingest.log`. |
| T-62-06 | Spoofing | Query scoping mistaken for an ongoing security filter | mitigate | The config doc comment, `resolveAccountQuery` JSDoc, and every `recense doctor` run all state the `backfill only` limitation; a source-level regression test locks in that `users.history.list` carries no `q`. Scoping is documented as scope control, never as an ongoing content filter. |
| T-62-SC | Tampering | npm/pip/cargo installs | mitigate | No package install in this plan — net-zero new runtime dependencies (verified milestone-wide). Nothing to gate. |
</threat_model>
