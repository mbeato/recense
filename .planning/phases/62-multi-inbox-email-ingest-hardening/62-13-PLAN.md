**The verification report's recommended VF-01 fix is REJECTED, with measured cause.** The report proposes
`blockContent.replace(/\/\*[\s\S]*?\*\//g, '')`. Applying exactly that during planning closes all three VF-01
shapes AND opens a new leak of the same contract: with the input

the naive strip deletes from the `/*` inside the first CSS string through the `*/` inside the last one, taking

it is a fifth bypass wearing a fix's clothes.

**A lazy-alternation regex form of the same fix is ALSO rejected, for a second measured reason: it is quadratic.**
The obvious string-aware repair — one module-scope regex alternating a double-quoted string, a single-quoted
string and a lazy `/*` ... `*/` comment, driven through a single `.replace()` — was prototyped and timed. On block
content shaped as `/*y` repeated, which contains no `*/` anywhere, every `/*` starts a lazy forward scan to end of
string that never finds its terminator, and the engine then advances one position and repeats:

| block content (inside a properly closed `<style>` pair) | 32 KB | 64 KB | 128 KB | 256 KB |
|---|---|---|---|---|
| `/*y` repeated — lazy-alternation `.replace()` | 47.8 ms | 203.8 ms | 749.0 ms | 3,009.5 ms |
| `/*y` repeated then `.legal{display:none}` — lazy-alternation `.replace()` | 47.1 ms | 187.3 ms | 753.5 ms | 3,017.6 ms |
| the same two shapes — LINEAR cursor scan | 0.3 ms | 0.2 ms | 0.5 ms | 0.9 ms |

Clean O(n^2) at ~4x per doubling, extrapolating to roughly 48 s at the 1 MiB bound plan 62-15 selects. The second
row is the sharper indictment: the shipped module handles that input in **0.1 ms today** (the trailing
`{display:none}` gives `RULE_RE` a brace to stop at), so the regex form would introduce a net-new quadratic on an
input that is currently fast — the NEW-01 pattern repeating one wave later, inside the wave meant to close it.
`stripCssComments` is therefore specified below as a linear cursor scan with no regex at all, mirroring the
RAWTEXT close-tag technique in this same task. Measured on the linear form: 1.9 ms at 512 KB for the same shape.

Per HTML §13.2.5.1-13.2.5.20, inside a raw-text or escapable-raw-text element the ONLY thing that can end the
element is its own end tag: `</` + the element's name, followed by whitespace, `/`, or `>`. Nothing else in the
body is a tag. Nesting is impossible, so the first matching end tag closes the element — this is why
`<script>var s = "</script>";</script>` famously ends at the first `</script>`. The current depth-counting scan
models neither rule.

The RAWTEXT / escapable-RAWTEXT element set to use: `script`, `style`, `title`, `textarea`, `iframe`, `noembed`,
`noframes`, `xmp`. `noscript` is deliberately EXCLUDED and the exclusion must be stated in the code: mail clients
parse with scripting disabled, where `<noscript>` content is ordinary markup, so the existing depth-counting scan
is the faithful one there — and stage 4 deletes the element wholesale either way.
