<the_layering_this_restores>
A browser decides "is this element hidden?" in two ordered layers:

  1. HTML: tokenize the start tag; decode character references in each attribute value.
  2. CSS:  tokenize the resulting `style` value; drop comments; decode ident escapes; read
           declarations.

recense currently implements neither layer at the attribute boundary — it regexes raw source text
once and calls it both. Plan 62-20 built layer 2 (the token-derived signature helper). This plan
supplies layer 1 and composes them in that order. The composition is what makes the four CR-07
payloads AND the CR-05c payload fall out of one mechanism rather than five special cases:

  style="display&#58;none"        -> layer 1 -> `display:none`        -> layer 2 -> hidden
  style="display&colon;none"      -> layer 1 -> `display:none`        -> layer 2 -> hidden
  style="display&#58;/*x*/none"   -> layer 1 -> `display:/*x*/none`   -> layer 2 -> hidden
  class="leg&#97;l"               -> layer 1 -> `legal`               -> matches harvested `.legal`

WR-13 (`class` split on JavaScript `\s` rather than HTML's five ASCII whitespace characters) is OUT
OF SCOPE as a finding and must not become an acceptance criterion. It may be closed incidentally if
the parser supplies the split — if so, record it as an incidental closure in the SUMMARY.
</the_layering_this_restores>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| attacker-authored attribute value -> hiding decision | The adversary chooses the encoding of every class/id/style value and will pick the one the scanner does not decode |
| `scanHtml().startTags` -> stage 4/5 removal ranges | A wrong range leaks hidden content or destroys visible prose; the parser's element model is now the sole authority |
| decoded attribute value -> CSS signature helper | The two layers must compose in the browser's order; composing them in the wrong order reopens both halves |

|-----------|----------|-----------|-------------|-----------------|
