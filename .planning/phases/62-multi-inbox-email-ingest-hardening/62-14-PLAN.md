<objective>
Close the algorithmic half of WR-02. `62-VERIFICATION.md` escalated it from "accepted residual" to a gap after
measuring an adversarially-shaped body against `dist/src/source/strip-hidden.js`:

```
 64 KB ->     1,983 ms
128 KB ->     7,904 ms
256 KB ->    31,616 ms
512 KB ->   126,422 ms  (2m 6s)
```

Clean O(n^2). A single crafted ~512 KB email — an unremarkable size for an HTML newsletter — stalls episode
ingestion for over two minutes, on input whose size and shape the attacker chooses.

**Planning-time root-cause measurement, which contradicts the report's own attribution.** The report attributes
the blowup to 62-12's `<`-permitting `ATTRS` fragment. Instrumenting each stage separately on the report's exact
shape (`<style>` + `a<x ` repeated + `</style>`) shows otherwise:

| stage | 32 KB | 64 KB | 128 KB |
|---|---|---|---|
| stage 2 `STYLE_BLOCK_RE` matchAll | 0.1 ms | 0.1 ms | 0.1 ms |
| **stage 2 `RULE_RE` matchAll over the block content** | **504.5 ms** | **2017.9 ms** | **8361.0 ms** |
| stage 4/5 `START_TAG_RE` scan | 0.2 ms | 0.1 ms | 0.4 ms |
| stage 6 `ANY_TAG_RE` replace | 0.1 ms | 0.1 ms | 0.2 ms |

`RULE_RE` is essentially 100% of the cost, and it has nothing to do with `ATTRS` or with `<`: `([^{}]+)` cannot
cross a brace, so its scan cost is bounded by the distance to the nearest brace — but a long BRACE-FREE run that
is not followed by `{` costs O(run) at every start position, so a `<style>` body with no `{` (or with a
brace-free tail) is quadratic. Isolated: `RULE_RE` alone over brace-free content measures 130 / 512 / 2017 /
8027 ms at 16 / 32 / 64 / 128 KB. Applying plan 62-13's NEW-01 fix changes this by **nothing** (measured
32,264 ms before vs. 32,323 ms after, at 256 KB) — so the "the NEW-01 fix may reduce the constant on its own"
hypothesis in the gap scope is measured FALSE and must not be relied on.

The second, smaller quadratic is real but separately located: every FAILING forward scan of the `ATTRS` region
runs to end of string. A scan that finds a `>` SUCCEEDS and moves `lastIndex` past it, so successful matches are
linear in aggregate; failing scans can only happen in the region after the LAST `>` in the document, where no
complete tag can exist. Stage 6 already deletes from the first `<` in that region to end of string. Doing that
truncation FIRST removes the entire failure region before any scan runs.

**Two exact linear bounds, both measured behavior-preserving during planning (0 output differences across the
shipped test corpus, 373 literals, and 80,000 generated markup-shaped inputs):**

| shape (512 KB unless noted) | before | after |
|---|---|---|
| `<style>` + `a<x ` repeated + `</style>` (the report's shape) | 126,422 ms (report) / 32,387 ms @256 KB (this machine) | **1.5 ms** |
| A `<div a="yyy…` | 3,728 ms @256 KB | 0.4 ms |
| B `<div a"b'c…` | 2,372 ms @256 KB | 0.5 ms |
| S `<style a="yyy…` | 4,819 ms @256 KB | 0.4 ms |
| U `<div a=b ` | 22,836 ms @256 KB | 0.4 ms |
| V `<style>{` + `y` repeated + `}</style>` (new) | 32,724 ms @256 KB | 0.9 ms |
| W `<style>` + `y` repeated + `}.legal{display:none}</style>` (new) | 32,301 ms @256 KB | 0.8 ms |
| T complete `<style …>` open tags, no `</style>` (T-62-54) | 28.3 ms @256 KB | 28.3 ms — **unchanged, still quadratic** |

**Two further shapes belong in the measured set, and did not appear in the report.** Plan 62-13 adds
`stripCssComments`, a scan over attacker-authored stylesheet content, and specifies it as a regex-free linear
cursor loop precisely because the obvious regex form is quadratic: measured during planning at 47.8 / 203.8 /
749.0 / 3,009.5 ms for 32 / 64 / 128 / 256 KB of `/*y`-repeated block content, versus 0.2-0.9 ms for the linear
form. A cost gap that is not measured is a cost gap that is assumed, and this phase has now shipped one defect per
wave on assumptions. So Shape X (`'<style>' + '/*y'.repeat(n) + '</style>'`), Shape X3 (the same with
`.legal{display:none}` before the close tag — the shape that is 0.1 ms on the pre-62-13 module and is therefore
the net-new-regression detector), Shape Y (`'<style>' + '"y'.repeat(n) + '</style>'`, the quote-state analog) and
Shape Z (`'<style>' + 'url(a'.repeat(n) + '</style>'`, the url-token analog — 62-13's scanner gained two further
forward-scanning cases for url-tokens and escapes, each of which is a place a repeated failing scan could hide)
join the measured set. If 62-13 shipped as specified these are confirmations that its bound holds; if it did not,
they are the discovery — either way they must be measured here, not inferred from 62-13's SUMMARY.

Purpose: a measured availability gap on attacker-controlled input, against the same module that carries roadmap
SC #3. Output: two exact linear bounds; a demonstrated (not asserted) behavior equivalence; cost assertions at
512 KB with numbers instead of adjectives; and the one remaining quadratic named with its own measurements.

- `RULE_RE` (`const RULE_RE = /([^{}]+)\{([^{}]*)\}/g;`) becomes unused and must be DELETED, not left as dead
  code. Its doc comment's information (plain CSS has no nesting) moves to the new scan.

Why the linear scan is exactly equivalent to `RULE_RE`'s left-to-right greedy match, stated so it can be checked
rather than trusted: a match's declaration body is `[^{}]*` terminated by a `}`, so within the text between two
`}` characters the body must begin after that segment's LAST `{`; the selector run is `[^{}]+`, so it must begin
after the preceding `{` (or at the segment start) and end at that same last `{`; and `[^{}]+` requires at least
one character, so a zero-length selector run is not a match — which is the same outcome as the existing
`selectors.length === 0` skip. `MAX_HARVESTED_SELECTORS` semantics are preserved by checking `total` at the same
two points as today.
