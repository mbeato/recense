<objective>
Carry each email's own send time — parsed from the `Date:` header the adapter already reads — through
the ingest path onto the episode row as `event_ts`, defended against a header an attacker controls.

Purpose: EMAIL-04, first half. `RawGmailMessage.headers.date` is populated at
`src/source/gmail-adapter.ts:217` and then explicitly discarded: its own doc comment at :54-55 says
"carried for completeness; not included in provenance string". Nothing in `src/consolidation/` has ever
referenced it. Meanwhile `episode.ts` records ingest time, which for a fresh account's backfill is
"whenever the backfill ran" — identical, to the millisecond, for hundreds of messages spanning months.
Without a distinct event time there is no basis on which a backfill batch can be ordered chronologically
at all. This plan lays that basis; plan 62-05 consumes it.

The `Date:` header is attacker-controllable, which makes the parse a security control rather than a
convenience: a future-dated header must not be usable to schedule stale evidence after newer state.

Output: an additive `episode.event_ts` column (SCHEMA_VERSION 16), the field threaded through
`NormalizedRecord` → `RecordEventParams` → `AppendEventParams` → the episode row, and
`parseEmailDate` with an explicit plausibility window.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| email `Date:` header → `event_ts` | The header is written by the sender. It is attacker-controlled data being converted into a value that will influence the order in which evidence is applied to beliefs (plan 62-05). This is an integrity control, not a formatting convenience. |
| adapter record → episode row | A new optional field crosses the D-58/D-59/D-60/D-63 adapter contract. It must not become a back door for salience hinting (D-60) or an alternative dedup key (D-59). |
| existing database → migrated database | Live installs carry real, irreplaceable graph data. The migration must be additive and non-destructive. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-62-23 | Tampering | Forged far-future `Date:` header used to apply stale evidence over newer state | mitigate | `parseEmailDate` returns null for any value beyond `nowMs + 48h`. Null excludes the episode from plan 62-05's chronological reordering entirely, leaving it in its ordinary salience-priority slot, so the "sort myself last" lever does not exist. Asserted by a test using a 2036-dated header and by the 24h-passes / 72h-rejected pair. |
| T-62-24 | Tampering | Forged far-past `Date:` header | accept | Documented as harmless in the same JSDoc: a past date sorts the forged evidence EARLIER, so genuine newer evidence is applied after it and wins under plan 62-05's ordering. A floor of 1990-01-01 still rejects epoch-0 and nonsense values so the ordering cohort is not polluted by obviously-bogus anchors. Accepted with stated reasoning rather than silently ignored. |
