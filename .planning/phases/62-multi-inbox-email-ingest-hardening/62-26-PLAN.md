<why_parse5_here_when_62_21_disqualified_it>
62-21 disqualified `parse5@7.3.0` for PRODUCTION on criterion C3 (totality): it throws
`RangeError: Invalid code point` in `Tokenizer._emitCodePoint` on 150/20,000 seeded hostile inputs,
reproducible on consecutive lone low surrogates. That disqualifier is about the online ingest path,
where attacker-controlled bytes reach the parser and a throw is an outage.

It does not transfer to a TEST oracle. The differential's generator owns its own alphabet: it emits
no lone surrogates, and 62-28's oracle is required to count any `parse5` throw as an explicit
`oracleUnavailable` case with an exact count rather than swallow it. What matters here is exactly the
property 62-21 measured and confirmed: parse5 is a spec-conformant HTML tokenizer/tree-builder with
correct `</style/>`, `</style foo>` and `<!>` handling — i.e. it is correct on precisely the shapes
htmlparser2 gets wrong, which is what makes it able to adjudicate production's use of htmlparser2.

Version choice is `7.3.0`, not `8.x`: `62-21-PLAN.md:73-74` records that `8.0.1` is ESM-only while
`7.3.0` ships dual CJS/ESM exports, and `7.3.0` is the exact version 62-21 already legitimacy-checked
and measured. Do not "upgrade while we're here."
</why_parse5_here_when_62_21_disqualified_it>

<runtime_dependency_invariant>
CLAUDE.md and STATE.md both carry "Net-zero new runtime dependencies" as a load-bearing engine
invariant. A `devDependencies` entry is not a runtime dependency: it is not installed by `npm ci
--omit=dev`, never reaches `dist/`, and cannot be imported from `src/` (the compile-time boundary
62-23 established and `62-VERIFICATION.md` proved by construction with a TS7016 probe). The invariant
holds. It stops holding the moment `parse5` appears in `dependencies` or is imported from any file
under `src/` — both are asserted against in this plan's acceptance criteria and must stay asserted.
</runtime_dependency_invariant>
