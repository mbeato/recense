## Migration mechanism — determined by source read, not guessed

**Verdict: drop the index IN PLACE inside the existing v16 block. Do NOT bump `SCHEMA_VERSION` to 17.**

Grounded in how this file's migration runner actually behaves (`src/db/schema.ts`, read directly):

1. `initSchema` has **no per-version gate**. Every migration block from v2 through v15 executes
   unconditionally on every call. Each is made idempotent by its own guard — `CREATE ... IF NOT EXISTS`,
   `DROP ... IF EXISTS`, or a `PRAGMA table_info` column check — never by a stored-version comparison.
2. `meta.schema_version` is read only at the very END of `initSchema` (`:649-665`), and serves exactly two
   purposes: throw when `stored > SCHEMA_VERSION` (the M-9 downgrade guard), and stamp when
   `stored === null || stored < SCHEMA_VERSION`. It never gates which DDL runs.
3. Therefore replacing the `CREATE INDEX IF NOT EXISTS idx_episode_event_ts` with
   `DROP INDEX IF EXISTS idx_episode_event_ts;` inside the v16 block WILL execute against the founder's
   already-at-v16 live database on the very next `initSchema` call. The drop lands with no version change.
4. This is precisely the **v5 migration precedent** already in the file (`:295-313`):
   `DROP INDEX IF EXISTS idx_node_eviction;` and `DROP INDEX IF EXISTS idx_activation_trace_ts;` sit inside a
   numbered migration block and run unconditionally the same way.
5. Bumping to 17 would be actively wrong: it changes no schema shape, forces a re-stamp for nothing, and
   breaks four hard-coded assertions — `tests/activation-sink.test.ts:51` and `:137`,
   `tests/schema-v11-migration.test.ts:57`, `tests/schema.test.ts:16` — plus the version-naming comments at
   `src/db/schema.ts:11` and `:38`. Editing those to keep a no-op bump alive is churn with negative value.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migration code → the founder's live already-migrated database | `initSchema` runs at every process start against a real DB holding real memory. A migration edit that only affects fresh DBs would leave the live DB carrying the dead index forever, silently failing to close the finding. |
| index drop → query planner | Dropping an index that some query actually depends on turns a hot path into a full scan. The justification for dropping rests entirely on "no SQL references `event_ts`", which must be verified, not assumed. |
| schema version stamp → downgrade guard | `SCHEMA_VERSION` participates in the M-9 downgrade guard that throws when a stale binary meets a newer DB. Changing it without cause creates spurious version skew. |
