<objective>
Close CR-02: stage 6 sweeps with a regex whose character class admits its own delimiter, before it
truncates the stray-`<` run the earlier stages just exposed.

Purpose: `ANY_TAG_RE` (`strip-hidden.ts:1468`, built from `ATTRS` where the unquoted class permits
`<`) runs via `.replace()` over the post-deletion string, and its own stray-`<` truncation runs AFTER
the sweep (`:1585-1587`). On a run of `<` with no later `>` the scan fails from every start position
after consuming the whole remaining tail — O(n squared). Stage 0's Bound A hoists exactly this
truncation, but runs BEFORE stages 3/4/5, and the file's own comment (`:112-113`) already knows those
stages "can expose a NEW stray `<` that stage 0 could not have seen." Deleting a single element or a
single comment is enough to strip every `>` from the tail.

Independently measured at HEAD: 2.5 / 20.0 / 262.1 / 4164.4 ms at n = 1k/4k/16k/64k — a clean
16x-per-4x curve — 4166.6 ms for the comment-only trigger, 68,242.9 ms at 256 KB, and 4080 ms
end-to-end through `normalizeGmailMessage` at a 64 KB body: 4x over the module's own 1000 ms budget at
1/16 of the permitted size, extrapolating to ~18 minutes at the 1,048,576 code units the adapter
admits. The sender chooses both the bytes and the size.

This falsifies 62-22's own must-have truth #4. `gmail-adapter.ts:384-407` re-derived the cap against a
29-shape set containing no "many `<` plus one removable construct" row, so "Every shape stays over 20x
under the 1000 ms budget" is a statement about the shape set, not about the cap — the same failure
mode as T62-91, which falsified 62-15 for exactly the same reason.

Output: the truncation hoisted to immediately before the sweep, the cap re-derived against the shape
family that falsified it, and cost gates that survive a shared CI runner.

<why_this_is_equivalent_not_just_faster>
The hoisted truncation deletes from the first `<` that follows the LAST `>` in the post-deletion
string. Everything from that index onward contains no `>`, so no complete tag can exist there and
`ANY_TAG_RE` can never match inside it. The existing post-sweep truncation (`:1586-1587`) already
deletes from the first `<` REMAINING after the sweep, which sits at an index less than or equal to the
hoisted one. The hoisted deletion is therefore a strict subset of what the existing fail-safe already
removes — same output, minus the failing-scan region the sweep would otherwise pay for.

Do not take that argument on trust. This phase's standing rule is that a containment argument living
only in prose is how leaks ship; prove it with Task 1's equivalence corpus.
</why_this_is_equivalent_not_just_faster>
