## Summary

Phase 39.1 is a pure-TypeScript internal refactor with no new external dependencies. It restructures the existing schema-anchored corpus (CorpusPromoter → chapter docs with schema-UUID slugs) into a content-driven taxonomy of LLM-named subject docs (many per project) + a single project-hub doc per scope. The existing write/generation pipeline (`corpus-promoter.ts`, `corpus-generator.ts`, `doc-writer.ts`, `run-sleep-pass.ts`) is largely reused — the restructure is in what triggers generation, how subjects are identified, and how hub↔subject containment is represented.

The exhaust-gate is the highest-complexity new capability: a two-stage mechanism that (1) harvests schema labels and atom membership from SchemaInducer's already-running output to decide subject candidacy and drift, then (2) pays for a dedicated Sonnet generation call only when a create or refresh gate opens. The tap point is AFTER `inducer.induceSchemas()` completes inside `consolidator.ts` Phase C — schema nodes with their human labels and `abstracts` edge members are available via SQL at that point with zero extra LLM cost.

Drift measurement is resolved by comparing `MAX(n.last_access)` over a schema's D-37-gated `abstracts` members against the doc stub's `node_doc.generated_at` — both are existing fields, no schema change required. The atom-count-since-gen signal can be derived by counting members with `last_access > generated_at` from the same joined query.

The junk-doc cleanup is the lowest-risk thread: fully deterministic SQL predicates, a reused snapshot path, and hard-delete is safe because docs are `origin='inferred'`, `s=0`, `c=1.0`, lifecycle-exempt regenerable nodes.

**Primary recommendation:** Build in the D-11 sequence. Subject proposal (LLM naming) is the critical new call; everything else adapts existing patterns. The stable-edge invariant (BUG-2c in `doc-writer.ts`) applies to hub↔subject edges too — write hub stubs before subjects and fill-in-place, don't tombstone-and-recreate.

### Pattern 1: Exhaust-Gate Signal Harvest

**What:** After `consolidator.consolidate()` finishes, schema nodes with human labels and their `abstracts` members are in the DB. The tap is a SQL-only read — no extra LLM call.

**When to use:** Always during sleep pass; gated by `RECENSE_CORPUS_GEN !== '0'` (same env gate already checked in `run-sleep-pass.ts:549`).

**The tap query (construct at planning time):**
```sql
-- For a given scope, find schemas whose gated members belong to scope S
-- and compare member freshness against the doc's generated_at
SELECT
  s.id              AS schemaId,
  s.value           AS schemaLabel,
  COUNT(m.id)       AS memberCount,
  MAX(m.last_access) AS latestMemberAccess,
  nd.generated_at    AS docGeneratedAt,
  nd.slug            AS existingSlug
FROM node s
JOIN edge e    ON e.src = s.id AND e.kind = 'abstracts'
JOIN node m    ON m.id  = e.dst
               AND m.type IN ('fact','entity')
               AND m.tombstoned = 0
               AND m.origin != 'inferred'
JOIN node_scope ns ON ns.node_id = m.id AND ns.scope = ?  -- scope param
LEFT JOIN node n_doc ON n_doc.type = 'doc' AND n_doc.tombstoned = 0
LEFT JOIN node_scope ns_doc ON ns_doc.node_id = n_doc.id AND ns_doc.scope = s.id
LEFT JOIN node_doc nd ON nd.node_id = n_doc.id
WHERE s.type = 'schema' AND s.tombstoned = 0
GROUP BY s.id, s.value, nd.generated_at, nd.slug
HAVING memberCount >= ?  -- minMass param
```

Source: [VERIFIED: direct read of corpus-promoter.ts stmtGetSchemaMembersWithValues, schema.ts node_doc DDL, run-sleep-pass.ts L482-488]

### Pattern 2: Drift Measurement — Existing Fields, Zero Schema Change

**What:** "Enough new/changed atoms since last gen" uses only fields that already exist:
- `node.last_access` (updated by `strengthen()` in Phase B) — freshness proxy for "this fact was touched/confirmed since last gen"
- `node_doc.generated_at` — write-once epoch ms when the doc was last generated; stable by design (ON CONFLICT preserves it per `semantic-store.ts:256-264`)

**Drift signal formula:**
```sql
-- Count of members that were touched AFTER the doc was last generated
SELECT COUNT(*) AS driftCount
FROM edge e
JOIN node m ON m.id = e.dst
           AND m.type IN ('fact','entity')
           AND m.tombstoned = 0
           AND m.origin != 'inferred'
           AND m.last_access > ?  -- node_doc.generated_at
WHERE e.src = ? AND e.kind = 'abstracts'
```

**Threshold shape (RESEARCH recommendation):** A count-based absolute threshold (e.g. `driftCount >= 3`) is simpler than a ratio and consistent with the PE-gated philosophy (it takes N new signals to trigger a refresh, not a fraction). Config knob: `corpusSubjectDriftThreshold` default 3. [ASSUMED — no prior art in codebase; consistent with highMass/lowMass shape]

**Why `last_access` works:** `strengthen()` in `update-decision.ts` calls `store.strengthen(nodeId, origin)` which bumps `last_access`. Every `confirm` or `extend` verdict during consolidation bumps the member's `last_access`. So `last_access > generated_at` cleanly means "this fact was actively confirmed or extended since the doc was written." [VERIFIED: consolidator.ts Phase B write path]

**Why NOT a separate counter:** Adding an `atoms_since_gen` column would require a schema migration and a write on every consolidation_event. The `last_access` comparison achieves the same signal with zero new tables or writes. [ASSUMED: design recommendation — no existing counter exists per grep]

### Pattern 3: Subject Identity and Stable Slug

**Critical for idempotency.** The subject-proposal LLM call MUST produce stable names across passes, or the same subject is re-proposed under a new name every pass (slug drift → stale doc accumulation).

**Recommended approach:** Slug = `${scope}:${normalizedSubjectName}` where `normalizedSubjectName` is lowercased, punctuation-stripped, space-to-hyphen. Example: `brain-memory:sleep-pass`, `brain-memory:retrieval`.

**Idempotency contract:**
- Before a subject proposal LLM call, query existing subject doc slugs for the scope.
- Pass them to the LLM prompt: "These subjects already exist: [list]. Propose additional subjects OR confirm that existing ones should be refreshed. Do NOT rename existing subjects."
- On return, match proposed names to existing slugs via normalization. Only propose new doc stubs for truly new names.

**Why this is harder than schema-UUID slugs:** Schema chapters used `schemaId` (a UUID) as slug — globally unique and stable across passes by definition. Subject names are LLM output and can vary in phrasing. The anchor-against-existing-list prompt strategy is the mitigation. [ASSUMED: design recommendation]

### Pattern 4: Hub Doc — Synthesized Overview + Subject Index

**What:** The hub doc is the project-scope landing doc (slug = scope string, e.g. `brain-memory`). It already exists in the system as the "landing-doc path" in `generateCorpusDocs()` (`corpus-generator.ts:200-220`). The restructure enriches it:

1. **Prompt augmentation:** The hub prompt gets a list of the project's subject slugs/names so it can write the index inline using `recense://doc/<docId>` refs.
2. **doc_containment edges:** Hub → each subject doc (parent→child), written by the subject promoter after stubs are created. Reuses `store.upsertEdge({ kind: 'doc_containment' })`.
3. **Stable-edge invariant:** Hub stub is created first. Subject stubs created second. doc_containment edges written third. All fill-in-place via BUG-2c path in `doc-writer.ts`. [VERIFIED: doc-writer.ts:90-110]

**Generation call:** `generateDoc(deps, scope)` — existing function, new hub-aware prompt via a new `buildHubDocPrompt(scope, factBlock, subjectDocs)`. About 1 Sonnet call per project per pass when REFRESH gate fires.

### Anti-Patterns to Avoid

- **Tombstone-and-recreate for hub/subject stubs:** The BUG-2c stable-edge invariant in `doc-writer.ts` requires fill-in-place for empty stubs. If the hub stub is tombstoned before being filled, the `doc_containment` edges from hub→subjects dangle (they reference a tombstoned node). Use `isEmptyStub ? effectiveDocId : docId` pattern from `doc-writer.ts:128-132`.

- **Schema UUID slugs for subject docs:** Subject docs MUST NOT use `schemaId` as slug (the old taxonomy). Subject slugs must be `scope:subject_name` format so they don't conflict with any new chapter-doc UUIDs the system might create.

- **Running cleanup before the restructure is defined:** D-09's "obsolete chapter doc" definition depends on the restructure. Cleanup must run after the new taxonomy is implemented (D-11).

- **Inferred output driving subject proposal:** The subject-proposal LLM call must query only `origin != 'inferred'` members (D-37 firewall). Subject docs generated from inferred facts would be self-confirming. The existing `stmtGetSchemaMembersWithValues` already enforces this. [VERIFIED: corpus-promoter.ts:171-175]

- **Subject proposals during online path:** Any subject name LLM call MUST run inside the sleep pass (offline). The online `/doc?slug=` path must never trigger a subject-proposal call — only stub lookup + lazy generation of already-proposed subjects. [VERIFIED: CLAUDE.md constraints — online paths LLM-free]

## Common Pitfalls

### Pitfall 1: Slug Drift — Subject Name Instability Across Passes

**What goes wrong:** The subject-proposal LLM call returns "Sleep Pass Mechanics" on pass 1 and "Sleep-Pass Flow" on pass 2. Two separate doc stubs are created for the same conceptual subject. The corpus fills with near-duplicate subjects.

**Why it happens:** LLM generation is non-deterministic; schema label variation across passes is the norm.

**How to avoid:** Always pass the list of existing subject slugs to the proposal prompt. Normalize the response before slug construction. Match against existing normalized slugs before creating a new stub. Design the prompt as "CONFIRM existing OR PROPOSE new, do NOT rename existing."

**Warning signs:** Growing number of subject doc stubs for a scope across consecutive passes without a corresponding growth in schema members.

### Pitfall 2: BUG-2c Stable-Edge Violation for Hub Stubs

**What goes wrong:** Hub stub is tombstoned (by `writeDoc`'s "tombstone prior live doc" path) when prose is generated. All `doc_containment` edges pointing FROM the hub to subject docs now reference a tombstoned node. The `/graph?type=doc` query excludes tombstoned nodes → the entire hub→subject edge set vanishes.

**Why it happens:** `writeDoc` has two paths: (1) fill-in-place for empty stubs (the correct path), (2) tombstone+recreate for non-empty docs (the `--force` regen path). If a stub gets a non-empty value written into it between stub creation and the prose-fill step, path 2 fires.

**How to avoid:** Hub stubs created by the promoter stay empty (`value=''`) until `generateCorpusDocs` fills them. Never write to a hub stub outside the standard generate path. The existing `isEmptyStub` check in `doc-writer.ts:131` handles this correctly IF the generation loop runs while the stub is still empty.

**Warning signs:** Hub doc appears in `/graph?type=doc` but has zero outgoing `doc_containment` edges.

### Pitfall 3: Self-Confirmation Via Inferred Schema Members

**What goes wrong:** The subject-proposal query includes `origin='inferred'` nodes (docs, insights) as schema members. The proposed subjects are influenced by previously generated docs. On the next pass, the docs strengthen, and the subjects change to reflect the docs' content rather than real facts. The brain converges on a hallucinated taxonomy.

**Why it happens:** Without the D-37 firewall (`origin != 'inferred'`), the corpus derivation loop is a self-reinforcing feedback cycle.

**How to avoid:** All queries for mass/member computation MUST include `AND m.origin != 'inferred'`. The existing `stmtGetSchemaMembersWithValues` in `corpus-promoter.ts:171-175` enforces this — copy this constraint verbatim into any new subject-query code.

**Warning signs:** Schema mass inflates across passes without corresponding new facts/entities from real episodes.

### Pitfall 4: FK Violation on Hard-Delete (Cleanup CLI)

**What goes wrong:** The cleanup CLI `DELETE FROM node WHERE id = ?` violates the FK constraint `node_doc(node_id) REFERENCES node(id)` (and same for `node_scope`). The delete fails with `FOREIGN KEY constraint failed`.

**Why it happens:** `node_doc` and `node_scope` FK to `node(id)` with no ON DELETE CASCADE. [VERIFIED: schema.ts — no CASCADE defined]. The deletion must happen in FK-safe order: child rows first, then parent node.

**How to avoid:** For each doc node to delete:
1. `DELETE FROM node_doc WHERE node_id = ?`
2. `DELETE FROM node_scope WHERE node_id = ?`
3. `DELETE FROM edge WHERE src = ? OR dst = ?` (dangling edges)
4. `DELETE FROM node_fts WHERE node_id = ?`
5. `DELETE FROM node WHERE id = ?`

All in a single `db.transaction().immediate()`.

**Warning signs:** `SQLITE: FOREIGN KEY constraint failed` error during delete.

### Pitfall 5: No-Rollback on Cleanup Failure

**What goes wrong:** Cleanup CLI deletes 15 nodes, then crashes. On manual inspection the wrong nodes were deleted. No snapshot was taken. No restore is possible (the no-DB-backup SPOF).

**Why it happens:** Snapshot was skipped or taken to the wrong path.

**How to avoid:** VACUUM INTO snapshot MUST succeed before any delete proceeds. If `VACUUM INTO` throws, abort immediately (same pattern as `runGraphHygiene:387-390`). Keep last 5 snapshots. Verify the snapshot file is readable before deleting a single row.

### Pitfall 6: Exhaust-Gate Tap Runs Before Schema Induction Completes

**What goes wrong:** The exhaust-gate reads schema labels before `inducer.induceSchemas()` finishes. New schemas from this pass are missing; old schemas from last pass are used. Subject proposal is stale.

**Why it happens:** The tap runs too early in the Phase C sequence.

**How to avoid:** The tap must run AFTER `await this.inducer.induceSchemas()` in `consolidator.ts:844` (which is already BEFORE `corpusPromoter.promote()`). The sleep-pass exhaust-gate hook in `run-sleep-pass.ts` runs AFTER `await consolidator.consolidate()` completes — so the full Phase C sequence (including `induceSchemas()`) has already finished. [VERIFIED: run-sleep-pass.ts:539-578]

## Open Questions (RESOLVED)

1. **Subject-proposal call: one LLM call per scope, or per schema?**
   - What we know: D-02 says "LLM looks at the project's atoms/schemas/episodes and proposes a small set of named subjects." One call per scope (batching all schemas) is cheaper; one call per schema is lower token cost per call but more calls.
   - What's unclear: Token volume of a per-scope call (might be large for big projects like `brain-memory`).
   - RESOLVED: Per-scope call, batching the top N schemas (by mass) as the input signal. Cap at the top 20 schemas by mass. Return JSON: `[{name: "...", relatedSchemaIds: [...]}]`. (Confirmed at plan time.)

2. **Hub doc prompt: include full subject body or just names?**
   - What we know: Hub = "synthesized overview + linked index." The index is a list of subject doc refs. The overview needs to know WHAT subjects exist.
   - What's unclear: Whether the hub LLM call needs the subject doc bodies (expensive: full Sonnet context) or just subject names (cheap).
   - RESOLVED: Subject names + a summary line only. Hub generates a navigation-layer overview; subjects hold the depth. Hub reads subject names from the existing `node_doc` slug list without fetching their value. (Confirmed at plan time.)

3. **Phase-39 `/index` route reuse for hub↔subject navigation**
   - What we know: Phase 39 built `#btn-index` + `/index` route showing docs grouped by scope. Hub↔subject containment is exactly this hierarchy.
   - What's unclear: Whether Phase 39 is already merged (and thus available) or still planned.
   - RESOLVED: Treat Phase-39 surfaces as available (they're in the v7.0 build per STATE.md). The hub doc's LLM-generated index section provides prose navigation; the `/index` route provides structural navigation. Both complement, neither duplicates. (Confirmed at plan time.)
