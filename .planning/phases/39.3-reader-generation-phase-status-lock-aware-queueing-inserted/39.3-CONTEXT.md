<domain>
## Phase Boundary

Reader/viz layer only. This phase changes how the doc-generation pipeline reports progress to the
reader and how the detached `generate-doc` CLI behaves under write-lock contention. It does NOT
touch the memory engine, the consolidation/write model, retrieval, or any online path. No new
node/edge types, no DB schema change, no online LLM cost.

### The bug being fixed (root cause, verified 2026-06-26)

A regenerate click on a busy engine produces: *"regeneration didn't complete — the generator timed
out or errored. The doc is unchanged; use 'regenerate' to try again."* — even though nothing timed
out. Trace:

1. Reader regenerate → `POST /doc/generate` → `spawnGenerateDoc(slug, force=true)` spawns the
   `generate-doc` CLI **detached with `stdio:'ignore'`** (`src/viz/server.ts:416-436`).
2. The CLI acquires the shared O_EXCL write lock **non-blocking**: `if (!acquireLock()) { stderr;
   process.exit(0) }` (`src/adapter/generate-doc-cli.ts:71-75`). When a sleep pass / corpus pass
   holds the lock, the CLI exits **0** — identical to success — before writing any log line (first
   `fileLog('starting…')` is at line 79, after the lock).
3. Because the child is detached + `stdio:'ignore'`, the read-only viz server can't see the exit
   reason. It returns 202 regardless; the reader polls, gets back the SAME old doc.
4. The reader's only failure signal is a `generated_at` comparison hack (`reader.js:483-526`,
   `fetchGeneratedAt` at 538-547): if `generated_at` didn't advance it shows the generic
   "timed out or errored" string. This conflates lock-contention with a real generation failure.

Evidence: `/tmp/recense-generate-doc.log` last entry 2026-06-24 (no line for the 06-26 click — the
lock-bail path is silent); a `sleep-pass-cli.js` process was holding the lock at click time.

### Generation pipeline phases (the real stages to surface)

From `src/reader/doc-generator.ts` (`generateDoc` ~322-374, `generateDocForSchema`) and the CLI
orchestration (`src/adapter/generate-doc-cli.ts:149-228`):

- **queued** — waiting to acquire the write lock (NEW: a wait, not a bail)
- **gathering** — `gatherFacts` / `gatherFactsForSchema` (+ embed query) — doc-generator step 1
- **generating** — `provider.generate(prompt, {maxTokens:4000})` — the long LLM call, step 3
- **verifying** — citation-verify + canonicalize — step 4
- **finalizing** — `writeDoc` + `DocGraphDeriver.deriveDocGraph()` — CLI steps 7/7b
- **done** — committed (reader gets 200 from `GET /doc`)
- **failed** — terminal error with reason

<decisions>
## Implementation Decisions (founder-approved — LOCKED)

### Approach: Child-owned status file + blocking lock-wait (Approach A)
- The detached CLI is the SOLE WRITER of a per-slug status file. The read-only viz server only
  READS it. This preserves T-27-11 (viz server DB handle stays read-only; all writes happen in the
  spawned CLI) and the existing detached/fire-and-forget spawn model.
- Rejected Approach B (server-owned queue + exit-code signaling): strictly more moving parts —
  it still needs the status file for per-phase, plus a server-side retry state machine that can
  drift from child reality. Rejected Approach C (minimal exit-code distinction, no per-phase):
  founder wants full per-phase granularity.

### D-1: New shared module `src/adapter/gen-status.ts`
Imported by both the CLI (writer) and the viz server (reader-only). Exports:
- `PHASES` = `['queued','gathering','generating','verifying','finalizing','done','failed']`
- `statusPath(slug)` → `/tmp/recense-gen-status/<hash>.json` where `<hash>` is a deterministic
  hash of the slug (e.g. `sha1(slug).slice(0,16)`). MUST be path-safe: a URL-supplied slug
  containing `../` or `/` cannot escape the status dir. Both server and CLI compute it identically.
- `writeStatus(slug, phase, extra?)` → atomic write of `{ phase, startedAt, updatedAt, error? }`
  (write-temp-then-rename, mirroring the lockfile's atomic discipline).
- `readStatus(slug)` → parsed status, or `null` if the file is missing OR **stale**
  (`updatedAt` older than ~15 min ⇒ treat a crashed child as absent).
- `clearStatus(slug)`.
All filesystem writes live here + in the CLI. `doc-generator.ts` stays FS-free.

### D-2: Lock-wait replaces lock-bail in the CLI
`src/adapter/generate-doc-cli.ts` — replace the instant `acquireLock()`-or-exit (lines 71-75)
with a **bounded wait loop**: write `queued`, poll `acquireLock()` every ~2s re-stamping `queued`,
until it wins OR the doc-gen timeout budget (`RECENSE_CLAUDE_HEADLESS_TIMEOUT_MS`, default 600000;
see CLI lines 129-138) elapses. On budget expiry → `writeStatus(slug,'failed',{error:'engine
stayed busy'})` then exit (founder chose give-up-after-budget over wait-forever). The lock-wait
loop SHOULD be factored into a testable unit. `lockfile.ts` `acquireLock()` semantics stay
unchanged (still non-blocking O_EXCL; the loop lives in the CLI).

### D-3: Per-phase callback into doc-generator (no FS in the reader module)
Add an OPTIONAL `onPhase?(phase)` callback param to `generateDoc` and `generateDocForSchema` in
`src/reader/doc-generator.ts`. They fire `onPhase('gathering')` before gather, `onPhase('generating')`
before `provider.generate`, `onPhase('verifying')` before citation-verify. The CLI wires
`onPhase → writeStatus`, and additionally writes `finalizing` around write+doc-graph, `done` after
commit (then `clearStatus`), and `failed` with the error reason in its catch block. doc-generator
emits semantic phase EVENTS only — it never touches the filesystem. (Hub/subject variants may take
the param for parity but regen only exercises generateDoc/generateDocForSchema.)

### D-4: Server forwards phase in the existing 202 envelope
`src/viz/server.ts` `send202Generating` (438-448) calls `readStatus(slug)` and emits
`{ status:'generating', phase, elapsedMs, error? }`. `elapsedMs` stays sourced from the in-flight
Set as today. The server's only new dependency is `readStatus` (read-only). When `readStatus`
returns a `phase:'failed'`, the 202 carries it so the reader can stop.

### D-5: Reader renders a phase stepper; silent-no-op hack is DELETED
`src/viz/modules/reader.js`:
- `startGenProgress` (300-335) becomes phase-aware: a stepper of the named phases with the active
  one highlighted + a live elapsed clock. The `generating` phase KEEPS the exponential
  time-estimate fill (the only phase worth estimating); the others render as discrete check-off
  steps. The prior pure-estimate bar is replaced.
- The poll loop reads `phase`/`error`: `phase:'failed'` ⇒ stop polling, show the real reason via
  `textContent` (keeps T-10-12 — never innerHTML DB/error strings). Anything else ⇒ update stepper.
- DELETE the `prevGeneratedAt` capture + `fetchGeneratedAt` (538-547) silent-no-op detection in
  `regenerate()` (483-534) and the generic "timed out or errored" string — the authoritative
  `failed` phase from the envelope replaces it.

### Status file lifecycle
Written at each transition. On `done`, reader gets 200 from `GET /doc` and stops; CLI `clearStatus`
after commit. On `failed`, the file persists so the 202 can report the reason; it is overwritten
when the next generation for that slug starts (writeStatus `queued`). Server treats `updatedAt`
> ~15min as absent (crashed child) so the reader never freezes on a stale stepper. The in-flight
Set in the server already dedupes spawns per slug (one child per slug).
