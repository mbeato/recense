<objective>
Compose the DRIFT-03 provenance-distinctness key: a pure function from (From: header, Gmail thread id, body text) to a session-id-shaped string that requires independence on **normalized sender identity + thread lineage**, with quoted/forwarded content stripped first.

**Not in this plan:** no adapter wiring (65-06), no mint-site change (65-07), no `countDistinctProvenance` change. This module is pure and directly unit-tested with plain strings.

**`normalizeSenderDomain(fromHeader)`** — order of operations is load-bearing and must be commented as such:
  1. `stripInvisibleCodepoints(fromHeader)` FIRST, imported from `./strip-hidden`. This mirrors `gmail-adapter.ts:517` exactly: `From:` is 100% sender-controlled and RFC 2047 encoded-words decode to arbitrary UTF-8, so a zero-width payload could otherwise fragment the parse and mint an attacker-chosen number of distinct "domains" from one real sender.
  2. Extract the first email address: prefer the content of the first `<...>` pair; if there is none, take the whole trimmed string. Take everything after the LAST `@` in that address (an address may legitimately contain a quoted local part with an `@`).
  3. Lowercase, trim, and strip one trailing `.` (FQDN form).
  4. Reject (return `null`) when the result is empty, longer than 253 characters (the DNS name bound), contains any character outside `[a-z0-9.-]`, contains no `.`, starts or ends with `.` or `-`, or contains `..`. **Reject, never truncate or sanitize** — a silently repaired domain is a distinct key an attacker chose, which is exactly the farming surface. State that reasoning in a comment.

  **No vendor domain knowledge of any kind.** No allowlist, no denylist, no ATS/job-board special cases, no "known recruiter domain" table. `tests/no-ats-domain-table.test.ts` walks all of `src/` and will fail the build if one appears, and the underlying reason (CLASSIFY-04 D-03: employers whitelabel ATS mail onto their own verified domains, so a fingerprint table degrades silently while looking correct in review) applies here identically. **`deriveGmailProvenanceKey(input)`** — returns either the composed key or `COLLAPSED_GMAIL_PROVENANCE_KEY`, never anything else, and never throws:
  1. **Residual gate (D-07) first.** `const residual = stripQuotedForwarded(input.bodyText);` then `if (isNearEmptyResidual(residual, input.minResidualChars)) return COLLAPSED_GMAIL_PROVENANCE_KEY;`. Running this first is deliberate: a pure forward contributes no independent provenance regardless of who forwarded it or which thread it landed in, and it is the reason three forwards of one thread count as one even when the three forwarding senders differ.
  2. `const domain = normalizeSenderDomain(input.fromHeader); if (domain === null) return COLLAPSED_GMAIL_PROVENANCE_KEY;`
  3. Validate `input.threadId` against a module-scope `THREAD_ID_RE = /^[A-Za-z0-9_-]{1,64}$/`; on failure return `COLLAPSED_GMAIL_PROVENANCE_KEY`. Gmail's server-assigned thread ids are hex, but do not hard-code hex-only — accept the conservative URL-safe set and reject everything else, including any string containing `:` (the key separator).
  4. Return `` `${COLLAPSED_GMAIL_PROVENANCE_KEY}:${domain}:${threadId}` ``.

  **Every failure path returns the SHARED collapsed key, never a per-message unique value.** This is the fail-closed direction: an unparseable message under-counts provenance (the belief holds longer), whereas any per-message fallback would restore exactly the farmable external_id behavior the "dangerous shortcuts" table bans. State this as a named invariant in the header.

**Discretionary choices to state and justify in the module header** (CONTEXT lists all four as planner discretion):
  - **Domain, not full address.** A single mailbox can trivially mint unlimited local parts (`a+1@`, `a+2@`), so keying on the address would let one sender manufacture N independent provenances. Keying on the domain reduces that to controlling N domains, which is the same bar as controlling N Claude Code sessions. The cost is honest and must be stated: two genuinely different humans at the same company corroborating the same status count as ONE provenance. That is the deliberate conservative direction — under-count, never over-count.
  - **accountId excluded.** The same thread landing in two of the founder's own inboxes is one piece of evidence, not two. Including `accountId` would double-count a CC.
  - **Plaintext, not hashed.** The sender domain already appears verbatim inside `episode.content`'s provenance header (`From: ... · Re: ... · Acct: ...`, `gmail-adapter.ts:521`), so writing it into `session_id` discloses nothing new, and a readable key is what makes Plan 65-10's dry-run reviewable by a human. The `[a-z0-9.-]` charset restriction plus the thread-id charset restriction is what makes `:` a safe separator without escaping.
  - **`ingest:gmail` prefix preserved.** The composed key extends the existing literal rather than replacing it, so any operator eyeballing `session_id` values still sees the source, and the collapsed fallback is a strict prefix of every composed key.

This module imports only from `./strip-quoted` and `./strip-hidden`. It must NOT import `EngineConfig` — the threshold arrives as a plain number parameter so the module stays trivially sweepable by the dry-run harness. It must NOT read `process.env` and must NOT touch a `Database`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `From:` header → provenance-distinctness key | Fully sender-controlled. RFC 2047 encoded-words decode to arbitrary UTF-8; display names can embed a fake angle-bracket address; domains can carry invisible codepoints. This value now partly determines whether a belief is force-destabilized. |
| email body → residual independence judgement | Fully sender-controlled. Whether the body is judged "new content" decides whether the message contributes a distinct provenance. |
| Gmail `threadId` → key | Server-assigned by Gmail, NOT sender-controlled (D-04 explicitly forbids reconstructing lineage from `References`/`In-Reply-To`, which ARE sender-controlled). This is the one trusted component of the key. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-65-04-SPOOF | Spoofing | Sender-domain forgery / rotation to manufacture distinct provenance | mitigate + accept residual | Keying on the DOMAIN rather than the address removes the free `a+1@`/`a+2@` local-part multiplication. Residual risk, accepted and documented in the module header: an actor controlling three sending domains can legitimately reach `contradictionN` — the same bar as controlling three Claude Code sessions, unchanged by this phase. Further bounded by `contradictionNBySource` (Plan 65-03) and by the fact that reaching N produces a belief update, not an external write (Phase 66 owns the human gate). |
| T-65-04-FARM | Tampering | Forwarded/quoted thread reused as N independent corroborations | mitigate | Residual gate runs FIRST, before sender and thread are even consulted, so a pure forward collapses regardless of forwarder identity.
