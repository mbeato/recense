## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test process → real HTTP server + real SQLite DB | The e2e spins the actual `createBrainHttpServer` with a real token and a temp DB |
| documentation → future third-party consumer | Wrong or incomplete docs become someone else's security defect in another repo |
| `evidence_quote` documented as consumable | Documenting the field without documenting its trust level invites a downstream injection |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-67-14 | Information disclosure | `tests/proposal-reference-e2e.test.ts` | mitigate | Test token is a local constant bound to a temp DB on 127.0.0.1 and an ephemeral port; temp DB, lock file, and adapter store are unlinked in `afterEach`; no real `RECENSE_SERVE_TOKEN` is read from the environment |
| T-67-15 | Spoofing | e2e auth case | mitigate | An explicit wrong-token case asserts the sync aborts and nothing leaves `pending`, locking the identical-401 discipline into a regression test rather than prose |
| T-67-16 | Tampering (downstream injection) | `docs/reference-client.md` | mitigate | The docs state the trust level of `evidence_quote` at the point the field is introduced — data, never instruction, never a decision surface, never interpolated into a prompt or command (D-07, 66 D-12) |
| T-67-17 | Repudiation / correctness | docs replay + refusal semantics | mitigate | Docs state that ids are deterministic, that re-delivery is expected, that approve on a terminal proposal is a 409 no-op rather than a second application, and that consumers must be idempotent on the proposal id — the defect class the e2e's replay case also locks |
| T-67-18 | Tampering | docs node-id carry-forward | mitigate | Documenting `entity_node_id`/`belief_node_id` as non-stable prevents a consumer from building a join key that silently points at a tombstoned node after belief-correction (64 D-08) |
| T-67-19 | Denial of service | documented consumer retry policy | mitigate | Docs classify exactly one status (503) as retryable and mark 400/404/409 terminal, so a documented consumer cannot build an unbounded retry loop against a permanently-refused proposal |
| T-67-SC | Tampering | npm installs | accept | Zero package-manager installs in this plan (test uses existing devDeps; docs are prose). `git diff package-lock.json` must be empty, so no legitimacy checkpoint applies |
