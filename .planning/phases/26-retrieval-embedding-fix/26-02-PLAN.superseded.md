Build the **extraction-replay KU harness** that RETR-02 validates against — the
piece that consumes the cached granite extractions (39,914 claims at
`~/.recense-eval-cache/eval01-n20-2026-06-16/`) and re-runs embed → consolidate →
retrieve → score WITHOUT re-extracting from granite (avoids the ~45h extraction cost).

IMPORTANT GROUNDING (verified against live code, not assumed): the existing
`src/eval/snapshot.ts` `replaySnapshots()` replays blessed `eval_snapshot`
query→answer rows (a retrieval-drift regression guard) — it is NOT the cached-claim
KU replay. The cache README itself states the replay path still "needs" to be built
(claims+episode_id → re-embed → re-consolidate). This plan builds that harness.

so it lands in parallel with diagnosis (Plan 01) and the swap (Plan 03), and is
dry-run-validated against the current small@1536 build before the swap exists. It
ALSO exposes a default-off `--embed-model` override so Plan 04 can run a clean,
controlled before/after at the identical harness even though by then DEFAULT_CONFIG
already reads `text-embedding-3-large` (the swap from Plan 03 lands in an earlier wave).
