## Summary

The root cause of intra-pass dedup blindness is confirmed and fully traced against the live source. During a single consolidation pass, `topk` (which drives candidate nomination) only scores nodes with `embedding IS NOT NULL AND tombstoned = 0`. When `applyDecision` mints a new node via `upsertNode`, that node enters the graph with `embedding = NULL` and `embedded_hash = NULL` (the dirty state set by `txUpsertNode` whenever a node is new or its value changed). `reembedDirty` runs only at pass START (line 453) and Phase C (line 832) — never during the per-episode judging loop. So a node minted by episode N is invisible to episode N+1's `topk` in the same pass.

The fix (Option D) is surgical: thread the already-computed claim vector (`claimVecs[claimIdx]`, a `Float32Array` computed in Phase A) into the `ClaimDecision` struct and call `setEmbedding(mintedId, decision.claimVec)` synchronously inside Phase B immediately after each `upsertNode` call that mints a node with `value == claimValue`. No async boundary is crossed. Eight mint sites exist in `applyDecision`; all should receive embed-on-mint.

**Primary recommendation:** Add `claimVec?: Float32Array` to the `ClaimDecision` interface, populate it at the two decision-fill sites (auto-unrelated and judge-verdict fill), and call `this.store.setEmbedding(mintedId, decision.claimVec)` after each of the eight `upsertNode` mint calls in `applyDecision`. The mandatory Task 1 invariant check is CLEAR — no downstream code depends on minted nodes being unembedded until Phase C.

### 4. setEmbedding — signature, behavior, and T-01-DIRTY

**File:** `src/db/semantic-store.ts:377`

```typescript
setEmbedding(id: string, vec: Float32Array, expectedValueHash?: string): void
```

Behavior:
1. Reads the node row via `stmtGetNode.get(id)`. Returns no-op if node not found.
2. **L-1 stale-vector guard:** If `expectedValueHash` is provided and ≠ `existing.value_hash`, no-ops. At mint time, do NOT pass `expectedValueHash` — there is no race since we're inside the same outer transaction.
3. **L-2 dims check:** First call stamps `embedding_dims` in meta; subsequent calls assert same dimensionality. This fires on the first `setEmbedding` call in a DB's lifetime. No issue.
4. Converts `Float32Array → Buffer` (preserving `byteOffset`, Pitfall 5).
5. Runs: `UPDATE node SET embedding = @embedding, embedded_hash = @embedded_hash WHERE id = @id` where `embedded_hash = existing.value_hash` — this marks the node clean (no longer dirty).

**T-01-DIRTY compliance:** `stmtSetEmbedding` is `private readonly` in `SemanticStore`. No code outside `setEmbedding()` can execute that prepared statement. Adding a second call site to `setEmbedding()` does NOT add a second writer of the underlying column — the single-writer invariant is about the SQL statement, not the number of call sites. [VERIFIED: live source]

**Read-your-own-writes inside the Phase B transaction:** `upsertNode` runs as a savepoint (better-sqlite3 uses `SAVEPOINT`/`RELEASE` for nested transaction calls within an active transaction). After the savepoint releases, `setEmbedding`'s `stmtGetNode.get(id)` will find the just-inserted node because SQLite guarantees read-your-own-writes within a connection. [VERIFIED: SQLite savepoint semantics, confirmed by better-sqlite3 docs]

interface ClaimDecision {

## Architecture Patterns

### Option D data flow (after fix)

```
Phase A
  provider.embed([claim1, claim2, ...]) → claimVecs[]
  ↓
  Per-claim: topk(claimVecs[i]) → candidates
  ↓
  Auto-unrelated: decisionSlots[i] = { relation:'unrelated', claimVec: claimVecs[i], ... }
  Judge-verdict:  decisionSlots[i] = { relation: verdict, claimVec: claimVecs[i], ... }

Phase B (db.transaction.immediate)
  for each decision:
    applyDecision(decision, episodeId)
      upsertNode({id: mintedId, value: claimValue, ...})
        → embedded_hash = NULL (dirty)
      setEmbedding(mintedId, decision.claimVec)  ← NEW
        → embedded_hash = value_hash (clean)
        → topk will now score this node
  markConsolidated(episodeId)

  Next episode in same pass:
    topk(claimVecs[j]) → finds mintedId from episode i (visible!)
    → judge can contradict/merge → contra >= 1
```

### reembedDirty post-fix scope

After embed-on-mint, Phase C's `reembedDirty` only processes nodes whose value was CHANGED by consolidation in this pass (e.g., `reconcile` path tombstones old node and calls `upsertNode` with a NEW id and new value — that new node has `embedded_hash = null` because it's a different claimValue, specifically `decision.claimValue` which IS in the claim vector... wait).

Actually, re-checking: for `reconciledId`, the minted node ALSO uses `value: decision.claimValue`. So the claim vector IS correct for it too. Embed-on-mint applies uniformly to all 8 mint sites.

The ONLY nodes that reembedDirty still needs to handle after the fix:
- Nodes from PREVIOUS passes that are newly dirty for unrelated reasons
- Seeded/cold-start nodes (which enter with `embedded_hash = null` by design)

## Common Pitfalls

### Pitfall 1: Wrong mint sites scoped
**What goes wrong:** Only applying embed-on-mint to `'unrelated'` and missing the 7 other paths. Extend-minted nodes and reconcile-minted nodes remain invisible to same-pass episodes that come later.
**Why it happens:** CONTEXT.md focuses on `'unrelated'` for the repro, but all 8 paths have the same structural bug.
**How to avoid:** Apply `if (decision.claimVec) this.store.setEmbedding(mintedId, decision.claimVec)` after all 8 `upsertNode` calls in `applyDecision`.

### Pitfall 2: Passing expectedValueHash at mint time
**What goes wrong:** Passing `sha256(decision.claimValue)` as `expectedValueHash` to setEmbedding and having the L-1 guard no-op because of a hash mismatch.
**Why it happens:** If `txUpsertNode` computes `value_hash = sha256(params.value)` but the caller computes the hash differently (different encoding).
**How to avoid:** Do NOT pass `expectedValueHash` at mint time. The node was just created in the same transaction — there is no race. The L-1 guard is designed for the reembedDirty path where a concurrent reconcile could change the value between capture and write-back.

### Pitfall 3: Missing L-2 dims check on first call to setEmbedding
**What goes wrong:** If the DB has never had setEmbedding called before (fresh test DB), the L-2 dims check will stamp `embedding_dims` in meta on the first mint-time call. This is correct behavior but can surprise tests that check the meta table.
**Why it happens:** L-2 runs on every setEmbedding call, stamping dims on first call.
**How to avoid:** Be aware that test DBs will have `embedding_dims` set after the first embed-on-mint. Tests asserting a clean meta table should account for this (or use a zero-dim MockModelProvider that doesn't trigger L-2 if dims=0... actually 0-dim is never valid). Not a real problem — just awareness.

### Pitfall 4: Assuming Phase C reembedDirty is no-op after the fix
**What goes wrong:** Removing or skipping Phase C `reembedDirty` thinking embed-on-mint covers everything.
**Why it happens:** Misreading the fix as "embed everything at mint time, so Phase C is redundant."
**How to avoid:** Phase C `reembedDirty` is still required for: (a) seeded/cold-start nodes that entered dirty before this pass, (b) nodes whose value was CHANGED by a write in Phase B that was NOT a new mint (e.g., if a future path modifies an existing node's value).

### Pitfall 5: Breaking the topkTombstoned path
**What goes wrong:** Accidentally embedding tombstoned nodes via embed-on-mint (e.g., in reconcile paths that tombstone an old node and mint a new one).
**Why it happens:** Tombstoning does NOT null the embedding (`stmtTombstone` only sets `tombstoned=1, training_eligible=0`). The old node's embedding is preserved for `topkTombstoned` (D-29/RET-02).
**How to avoid:** embed-on-mint is called only for NEWLY MINTED nodes (freshly generated `newId()`). Old nodes that are tombstoned by `this.store.tombstone(decision.bestCandidateId)` are untouched. No change needed.

**Scenario to reproduce (mirrors 35-pass-proof.cjs Scenario A):**

```typescript
describe('DEDUP-01: embed-on-mint intra-pass visibility', () => {
  it('same contradiction pair in ONE pass yields contra=1 after fix', async () => {
    const h = makeHarness();

    // embedFn: both A and B claims get a distinct non-zero unit vec at dim 0.
    // This makes their cosine = 1.0, clearing the 0.3 unrelatedSimilarityThreshold.
    // Important: reembedDirty at pass START sees an empty graph (no pre-existing dirty
    // nodes), so it does nothing. The only embeddings written in this pass come from
    // embed-on-mint (DEDUP-01 path under test).
    const unitVec = (dims: number) => {
      const v = new Float32Array(dims); v[0] = 1.0; return v;
    };

    const provider = new MockModelProvider({
      // Both A and B claims get the SAME unit vector.
      embedFn: (_text: string) => unitVec(h.config.embeddingDimensions),
      // Episode A: no candidates (graph empty) → auto-unrelated → no judge call.
      // Episode B: A's node visible via topk (cosine=1.0 > 0.3) → judge escalation.
      judgeScript: [
        // Episode B judge call: one candidate (A's node) → contradict
        { relation: 'contradict', best_candidate_id: '<placeholder>', magnitude: 0.8, contradicted_ids: [] },
      ],
      generateScript: [
        // Episode A extraction: one claim
        JSON.stringify([{ type: 'fact', value: 'Claim A content here' }]),
        // Episode B extraction: one claim
        JSON.stringify([{ type: 'fact', value: 'Claim B content here' }]),
      ],
    });

    // ... (append two episodes, consolidate once, assert contra=1)
  });
});
```

**Key details:**
- `judgeScript[0].best_candidate_id` must be set to the actual candidate id returned by topk. Since the judge mock receives `candidates: [{id, value}]`, the test can capture the id from the mock invocation or simply use `'confirm'` on the mock and assert tombstone count.
- Simpler approach: script the judge to return `'contradict'` and in the assertion check `SELECT COUNT(*) FROM node WHERE tombstoned = 1 >= 1` OR check the `consolidation_event` table for `event_type LIKE 'contradict%'`.
- The `best_candidate_id` in the mock verdict will be filtered against `candidateIdSet` (T-FK-01 guard at line 754). The mock's verdict id must match an actual candidate id. The established test pattern for this is to set up a pre-seeded node and use its id — but for the dedup test, A's minted node id is generated at runtime. Better: use `MockModelProvider` that captures the candidates passed to `judge()` and returns the first candidate's id as `best_candidate_id`.

**Alternative assertion (simpler):** Count `SELECT COUNT(*) FROM node WHERE tombstoned = 0` and `WHERE tombstoned = 1`. After the fix, a `reconcile` verdict tombstones A's node and mints a new one → `tombstoned = 1` count should be 1. Or check `consolidation_event` for any `event_type` starting with `'contradict'`.
