<objective>
Build the standalone, reusable entity-resolution seam: a **three-channel union candidate generator** (exact/entity-keyed ∪ BM25 lexical ∪ dense cosine) plus a **confident-or-null** resolver over it (score floor + top-2 margin). Deterministic, LLM-free, strictly read-only over the graph.

This is a standalone module (D-01) rather than inline code because Phase 69 (Entity-Anchored Ambient Recall) explicitly reuses this generator — an inline implementation would force a second divergent generator, exactly what ROADMAP warns against.

Purpose: never let "closest" stand in for "correct" (Pitfall 4). A missed resolution costs nothing; a wrong one silently corrupts an external system of record recense cannot fix.
Output: `src/consolidation/entity-resolution.ts`, two dark config knobs, and a unit suite that proves each channel can carry a resolution alone.

**Not in this plan:** no consolidator wiring, no `ClaimDecision` fields (that is 64-03). This module is standalone and directly unit-tested.
</objective>

Create `src/consolidation/entity-resolution.ts` exporting a class `EntityResolver` plus the pure helper `lexicalScore` and the types `EntityCandidate` and `ResolutionResult`.

**Constructor:** `constructor(db: Database.Database, store: SemanticStore, config: EngineConfig)`. It MUST NOT accept a `ModelProvider` — that omission is the type-level guarantee behind D-04 (zero net-new LLM calls); say so in the file header. Prepare two read-only statements in the constructor, mirroring `entity-dedup.ts:144-149`:
  - `stmtCandidateNodes`: `SELECT id, value, embedding FROM node WHERE tombstoned = 0 AND (@type IS NULL OR type = @type) ORDER BY id`
  - `stmtFtsCandidates`: `SELECT f.node_id AS id, n.value AS value FROM node_fts f JOIN node n ON n.id = f.node_id AND n.tombstoned = 0 WHERE node_fts MATCH @q AND (@type IS NULL OR n.type = @type) ORDER BY rank LIMIT @k`

The `@type IS NULL` form keeps the generator seam type-agnostic for Phase 69 reuse while letting this phase's caller pass `'entity'` (D-11: the resolution use filters to live `type='entity'` nodes; the seam itself does not hard-code that).

**Module-private constant:** `const ENTITY_CANDIDATE_K = 5;` — the per-channel cap for the BM25 and dense channels, matching the `candidateK` / `entityAnchorK` / `bm25CandidateK` calibration placeholders. Private, not config (Phase 55-01 D-01/D-02 precedent); Task 3 guards the literal behaviorally.

**`lexicalScore(a: string, b: string): number`** — pure, exported, no DB access. Tokenize `normalizeValue(a)` and `normalizeValue(b)` on whitespace into `Set<string>`, return the Dice coefficient `2 * |A ∩ B| / (|A| + |B|)`, and `0` when either set is empty. Dice is chosen over containment deliberately: containment scores "Stripe" against "Stripe Backend Role" as 1.0 and over-resolves, while Dice is symmetric and errs toward abstention (D-05). Import `normalizeValue` from `./normalize` — do not reimplement normalization (the codebase requires all normalization-dependent comparisons to agree).

**`generateCandidates(opts: { text: string; vec?: Float32Array; nodeType?: string; k?: number }): { candidates: EntityCandidate[]; channelCounts: { exact: number; bm25: number; dense: number } }`** — the reusable union seam. Three independent channels, deduped across channels by node id via a `Set<string>` (mirroring `cosineIdSet` in consolidator.ts:781), each contributing candidates and recording which channels found it in `EntityCandidate.channels`:

  1. **exact / entity-keyed** — call `store.resolveEntityByName(opts.text.trim())`; on a non-null id, fetch the node via `store.getNode(id)` and admit it (skip it when `nodeType` is set and the node's type differs). This is the shipped priority ladder (exact entity → exact any-type → length-capped contains), reused rather than reimplemented per D-02.
  2. **BM25 lexical** — `ftsQueryFromText(opts.text)`; when it returns null, skip the channel. Otherwise run `stmtFtsCandidates` inside a `try { } catch { }` whose catch body is empty except for a comment naming FTS-table-absent and MATCH-syntax-error graceful degradation (verbatim precedent: consolidator.ts:833-835, topk.ts `hybridTopk`). Cap at `opts.k ?? ENTITY_CANDIDATE_K`. Never build the MATCH argument by string concatenation and never pass raw descriptor text — `ftsQueryFromText` is the only path to MATCH.
  3. **dense cosine** — when `opts.vec` is absent, skip the channel entirely (this is the normal case for a caller with no embedding, and the "never dense-only" property must hold with this channel empty). Otherwise scan `stmtCandidateNodes`, decode each non-null `embedding` buffer with the `entity-dedup.ts:104-107` shape, guard on `byteLength % 4 === 0` and decoded `length === vec.length`, score with `cosineSimF32`, keep the top `opts.k ?? ENTITY_CANDIDATE_K` by score.

**Clamp the cosine explicitly: `const dense = Math.max(0, cosineSimF32(vec, decoded));`** `cosineSimF32` (topk.ts:226) returns the raw cosine in `[-1, 1]` — it is NOT pre-clamped. Without this clamp an opposed vector yields a negative score, which breaks two things at once: the `[0, 1]` score domain the floor and margin are calibrated against, and the `entityResolutionFloor > 1.0` dark-off switch (which is only unreachable-by-construction if scores are bounded above by 1). Also coerce any non-finite value to 0 with `Number.isFinite` as cheap defense against a malformed stored embedding — note that `cosineSimF32` already returns 0 for a zero-norm vector via its own `denom === 0` guard, so this is belt-and-braces, not the primary concern; the primary concern is the negative half of the range.

Score every candidate as `score = max(lex, dense)` where `lex = lexicalScore(opts.text, candidate.value)` and `dense` is the clamped-to-`[0,1]` cosine (0 when the dense channel is unavailable for that node). `max` is load-bearing for RESOLVE-01: it lets a lexical-only hit and a dense-only hit each carry a candidate over the floor independently, which is exactly the never-dense-only property. Store `lex`, `dense`, and `score` on `EntityCandidate` so tests and the caller can attribute an outcome to a channel.

**`resolve(opts: { descriptor: string; vec?: Float32Array }): ResolutionResult`** — the confident-or-null decision (D-04, both halves of Pitfall 4's prescription), calling `generateCandidates` with `nodeType: 'entity'`:
  - sort candidates by `score` descending, tie-broken by `id` ascending (determinism — a second run over unchanged state must produce the identical outcome)
  - zero candidates → `{ resolved: false, reason: 'no-candidates', channelCounts }`
  - `top.score < config.entityResolutionFloor` → `{ resolved: false, reason: 'below-floor', topScore, channelCounts }`
  - two or more candidates and `top.score - second.score < config.entityResolutionMargin` → `{ resolved: false, reason: 'margin-too-close', topScore, channelCounts }`
  - otherwise → `{ resolved: true, nodeId: top.id, descriptor: top.value, score: top.score, channelCounts }`. `descriptor` is the resolved node's own canonical `value` string verbatim, per D-08 / ARCHITECTURE Q4 — consumers key on the descriptor semantically. Never a consumer id, never a transformed or prettified string.

**Read-only contract (D-12):** the module must never call `upsertNode`, `upsertEdge`, `strengthen`, or `tombstone`, never mint an entity on a miss (an unknown company MUST abstain — Pitfall 4 failure mode 2), and never open a transaction. Its only SQL is the two SELECTs above plus reads through `store`.

**File header** must state, in the `entity-dedup.ts` header style: the D-IDs implemented (D-01/D-02/D-04/D-05/D-08/D-11/D-12), the zero-LLM guarantee and why it is type-level (no `ModelProvider` in the constructor), the read-only guarantee, the Phase 69 reuse contract for `generateCandidates` (type-agnostic seam, `nodeType` opt-in), and the **known precision limits stated honestly**: (a) callers that pass `vec` typically pass the embedding of the surrounding claim text rather than of the descriptor itself, so the dense channel is a proxy signal — the exact and BM25 channels carry descriptor-precise evidence; (b) same-company multi-role granularity ("Stripe — Backend" vs "Stripe — Platform") is merged into one node by the Phase 25 entity-dedup pass, so resolving both to that one node is honest, and per-role splitting is a Phase 65+ concern gated on measurement — do not "fix" entity-dedup here.
